# Договор и согласие

Доверенность говорит сервису, что разрешено. Она не говорит, сколько стоит аренда, что арендатору запрещено, какой у агента профиль и на каких условиях обрабатываются данные. Эти условия хранит договор: точные байты, которые подписали обе стороны. Глава разбирает договор аренды на открытом примере, подписи согласия, оплату, место каждого предела, условия срока и правил и роль третьих сторон.

Пример взят из набора проверочных данных стенда: каталог `experiments/rental-booking/testdata/wire-v2/nmc` репозитория `swarma-chain-lab`. Набор собран для сети regtest; платёж в нём синтетический.

## Договор аренды

Договор аренды это объект JSON с полями в точном порядке, без пробелов и перевода строки. В примере это файл `contract.json` длиной 1133 байта. Его поля:

```text
version          2
booking_id       33333333…33333333
renter_pubkey    f9308a01…bce036f9
renter_name      ""
agent_pubkey     e493dbf1…e8c4cd13
station_name     id/station-one
not_before       2000003600
not_after        2000007200
allowed          ["deliver","pay"]
forbidden        ["publish","repository.push","secret.release"]
budget_sat       10000
template_id      demo
template_sha256  6bf74fc1…7963620b
profile_id       curator-test
profile_version  1.0.0
profile_sha256   216a96ce…de4c43f0
payment          (ниже)
payment_policy   advance
privacy_sha256   ebbb4f6f…a066065c
```

Поля договора значат следующее.

| Поле | Значение |
| ------- | --------------------- |
| `booking_id` | Идентификатор брони, 32 байта. |
| `renter_pubkey`, `renter_name` | Ключ арендатора и его необязательное имя Namecoin. Ключ станет `grantee_key` доверенности. |
| `agent_pubkey` | Ключ сообщений агента. |
| `station_name` | Имя агента в Namecoin. |
| `not_before`, `not_after` | Окно аренды. В примере оно длится 3600 секунд. |
| `allowed`, `forbidden` | Разрешённые и запрещённые действия из словаря доверенности. Списки не пересекаются. Действие, которого нет ни в одном списке, не разрешено. |
| `budget_sat` | Бюджет действий агента в атомарных единицах NMC. |
| `template_id`, `template_sha256` | Шаблон договора и хэш его текста. |
| `profile_id`, `profile_version`, `profile_sha256` | Профиль агента, который запускается в слоте: имя, версия и хэш. |
| `payment` | Условия оплаты. |
| `payment_policy` | Когда начинается аренда относительно оплаты. |
| `privacy_sha256` | Хэш уведомления о приватности, которое арендатор видел в ответе `terms`. |

Условия оплаты это вложенный объект с собственным порядком полей:

```text
coin                  nmc
network               regtest
genesis               0f9188f1…466e2206
price_usd_cents       100
usd_micros_per_coin   1000000
rate_as_of            2000000000
max_rate_age_seconds  60
amount_atoms          100000000
address               muowReuD37GjLG1KPJxYR7RGf5C9tZc3z6
min_confirmations     2
```

Цена задана в центах доллара, курс в миллионных долях доллара за монету. Сумма в атомарных единицах монеты вычисляется с округлением вверх и фиксируется при создании брони:

```text
amount_atoms = ceil(price_usd_cents * 10^12 / usd_micros_per_coin)
             = ceil(100 * 10^12 / 1000000) = 100000000
```

Монета оплаты выбирается из NMC, BTC и LTC. Бюджет `budget_sat` от неё не зависит и всегда считается в NMC: арендатор платит за аренду одной монетой, а агент тратит по доверенности другую.

Хэш договора `contract_sha256` это SHA-256 точных байтов объекта. В примере:

```text
a759d6d6e7e6052ae092ad41f88570d2fdce59c43ba95ba55d1ee22de76ea66f
```

Любое изменение условий, включая сумму и адрес оплаты, меняет хэш и требует нового согласия.

## Согласие

Согласие арендатора это событие Nostr вида 8181 с пустым содержимым. В примере это файл `consent.json`:

```text
id          6c8bbb5c…b9346de6
pubkey      f9308a01…bce036f9
created_at  2000000000
kind        8181
tags        ["t","swarma-rental-consent-v1"]
            ["contract","a759d6d6…e76ea66f"]
            ["booking","33333333…33333333"]
            ["privacy","ebbb4f6f…a066065c"]
content     ""
sig         c0bed50b…638ef4a9
```

Тегов ровно четыре, в этом порядке. Ключ события равен `renter_pubkey` договора. Идентификатор события вычисляется по NIP-01: SHA-256 от компактного массива JSON `[0,pubkey,created_at,kind,tags,content]`. Арендатор подписывает этот идентификатор по BIP-340.

Согласие сделано событием, потому что у арендатора ключ Nostr, а расширение браузера по NIP-07 умеет подписывать только события. Подпись события покрывает хэш договора косвенно: хэш входит в тег, тег входит в идентификатор, идентификатор подписан.

Согласие доказывает две вещи. Арендатор согласился ровно на эти условия: потом ни одна сторона не может утверждать, что договаривались иначе. И арендатор владеет ключом, на который выдаётся доверенность: без согласия арендодатель мог бы выдать доверенность на чужой ключ.

С другой стороны договор подписывают два ключа арендодателя. Ключ поставщика в службе бронирования подписывает хэш договора и публикует пакет бронирования, событие вида 8182 с договором и согласием. Ключ доверенностей у подписанта подписывает сами 32 байта `contract_sha256`; эта подпись называется `landlord_sig` и входит в доверенность вместе с событием согласия. Подписи связаны так:

```text
байты договора -> contract_sha256
  |
  +-> арендатор: событие 8181 -> id -> sig
  +-> поставщик: пакет бронирования, событие 8182
  +-> ключ доверенностей: подпись хэша -> landlord_sig
        |
        +-> consent внутри доверенности
              |
              +-> подпись доверенности -> grant_id
                    |
                    +-> хэш выдачи в цепочке
```

Проверяющий доверенности сверяет совпадение хэшей, точные теги, подпись арендатора и подпись арендодателя. Согласие не может быть создано позже момента проверки и не может быть создано в конце окна или после него.

## Бронь и оплата

Бронь удерживает слот на время оплаты. Удержание по умолчанию длится 1800 секунд. Бронь, которая истекла без выдачи, освобождает слот.

Платёж это один выход на адрес из договора на сумму не меньше `amount_atoms`. Мелкие выходы не складываются. Служба бронирования засчитывает платёж, когда он подтверждён в активной цепочке монеты до истечения брони. Платёж в мемпуле оставляет бронь в ожидании: неподтверждённую транзакцию можно заменить, в том числе ту, что не объявляла о замене. Сбой чтения ноды состояния платежа не меняет.

Подписант перед выдачей проверяет платёж сам, на ноде монеты из собственной доверенной таблицы. Он применяет свои минимумы подтверждений и возраста курса; подписанный запрос на выдачу не может их ослабить.

Поздние, повторные и недостаточные платежи служба бронирования не приписывает следующему арендатору и не возвращает сама: она сохраняет их для разбора оператором.

Если блок с засчитанным платежом исчез из активной цепочки, служба бронирования добавляет запрос на отзыв, и подписант тратит печать. Старая доверенность не выдаётся заново, даже если тот же платёж вернулся в цепочку.

Так поступает стенд. По решению владельца различаются два случая; третью строку таблицы добавляет поправка к LIP-0008:

| Что нода показывает о засчитанном платеже | Что делает выдавший |
| ------------------------ | ---------------- |
| Та же транзакция платежа остаётся действительной: она снова в мемпуле или подтверждена в другом блоке | Ждёт N блоков нового подтверждения платежа и ничего не отзывает |
| Те же монеты потрачены другой транзакцией | Отзывает: тратит печать |
| Состояние платежа установить не удалось: нода недоступна или транзакции нет в мемпуле, а другой траты тех же монет не видно | Ничего не отзывает и читает снова: отсутствие транзакции другой траты не доказывает |

Число N задаёт профиль оплаты, и значение ему не выбрано. Что делает выдавший, если платёж остаётся действительным и не подтвердился за N блоков, не решено.

## Где записаны пределы

Предел аренды записан в трёх местах, и у каждого места своя задача.

| Где | Что записано | Кто проверяет и зачем |
| --- | --- | --- |
| Доверенность | Бюджеты аренды: монеты; запросы, токены и стоимость модели; наибольшая длина ответа | Каждый сервис по доверенности. Доверенность подписана и закреплена, поэтому сервис сверяет предел без текста договора и без доверия к шлюзу. |
| Договор | Те же пределы человеческим текстом и полями | Арендатор до согласия. Он подписывает именно эти числа, и в споре предъявляется договор. |
| Конфигурация сервиса | Потолки оператора: потолки подписанта, наибольший расход на один слот | Сам сервис. Потолок защищает оператора от ошибки в шаблоне договора и от взлома соседней службы. |

Договор повторяет каждый предел доверенности: исполнителя, вид, ресурс, единицу и величину. Несовпадение даёт отказ. Договор может содержать дополнительные условия для людей, но расширить подписанные пределы он не может.

Пределы аренды живут в доверенности, потому что только она доходит до каждого сервиса в неизменном виде. Потолки оператора живут в файле конфигурации каждого сервиса, который устанавливается вместе с машиной: они не зависят от конкретной аренды, и арендатор на них не влияет.

Сам сервис свою конфигурацию изменить не может. Конфигурация входит в запечатанный установочный пакет. Файлом владеет администратор машины, группа сервиса читает его без права записи: файл имеет права `0640`, каталог `0750`. Перед стартом сервис сверяет хэш конфигурации с манифестом пакета и при расхождении отказывается работать. Потолок меняется только новым пакетом после ревью. Правило защищает файл потолков от записи: ни агент, ни соседняя служба, ни процесс самого сервиса его не перепишут. Исполняет потолок сам сервис, и доверие к сервису остаётся. Взломанный сервис, который держит ключ API или денежный ключ, действует этим ключом в обход собственной проверки, и неизменный файл его не останавливает.

Расход внутри окна считает тот сервис, который исполняет действие. Как устроен его журнал и что происходит при потере журнала, разбирает глава "Сервисы по доверенности".

## Срок, период и правила

Решения владельца добавляют в договор три условия. Договор стенда их не несёт.

Срок найма задаётся в высотах блоков и покрывается одной доверенностью. Договор стенда называет одно окно в секундах; в примере оно длится час.

Период это отрезок внутри срока, по которому считаются пределы и оплата: столько-то запросов за период, столько-то монет за период. Что следует за неоплаченным периодом, говорит договор. Протокол даёт выдавшему одно средство: трату печати.

Правила модерации входят в договор хэшем своего текста. Рядом договор называет модератора: ключ, которым подписываются вердикты, и того, кто за ним стоит, модель или человека. Текст правил говорит, что считается нарушением и какое нарушение прекращает договор. Возврат предоплаты после прекращения тоже условие договора. Порядок прекращения дан в главе "Отзыв и наблюдение цепочки", раздел "Прекращение по нарушению".

## Что договор доказывает

Подписанный договор доказывает, что эти ключи приняли эти байты, а запись выдачи доказывает, что связка существовала к определённому блоку.

Договор не доказывает, кто стоит за ключом в обычном мире, справедливы ли условия, прочитан ли текст и выполнена ли работа. Он не доказывает и своевременности: предложение можно закрепить после его срока. В споре связь ключа с человеком подтверждают другие данные: удостоверение, переписка, платежи.

Для спора через годы пакет хранят целиком: договор, подписи, доверенность, доказательство из цепочки. Хэш не сохраняет потерянного.

## Произвольный договор

Договор аренды имеет точный формат. Договор на работу, которую нельзя формализовать, остаётся текстом. Алиса нанимается делать сайт для компании "Червы"; оценку "сайт сделан хорошо" программа из подписей не выведет.

Стороны поступают так же, как в аренде. "Червы" подписывают точные байты как предложение со сроком ответа. Алиса подписывает те же байты; изменённый текст это новое предложение. Подписи складываются в пакет, и его хэш записывается в цепочку одной транзакцией с выходом `OP_RETURN`. Заплатить за запись может любая сторона.

К произвольному договору добавляют соль, случайные данные, и хэшируют пакет вместе с ней. Без соли короткий договор подбирается перебором по хэшу. В договоре аренды соли нет: его формат фиксирован, и добавленное поле изменило бы подписываемые байты. Чтобы показать арбитру один пункт, договор собирают из пунктов с отдельной солью и раскрывают нужный; остальные видны как существующие. Такая проверка не доказывает, что в скрытых пунктах нет исключений.

По записи в цепочке не видно, кто договаривался: хэш не называет ключей. Если стороны хотят, чтобы согласие обеих показывала сама цепочка, запись тратит общий выход, который тратится только двумя подписями вместе. Это стоит ещё одной транзакции и раскрывает ключи сторон.

Подход описан в работе о рикардианских контрактах 2004 года: читаемый человеком документ, подписи и хэш, который связывает документ с действиями.

## Договор как объект

Договор аренды и произвольный договор это один и тот же объект: документ в точных байтах, который подписали две стороны или больше. Доверенность видит договор только как хэш, а двум сторонам, которые договорились без доверенности, нечего было бы закрепить в цепочке. Поэтому у договора собственное устройство, одинаковое для всех видов договоров. Его части названы по смыслу.

| Часть | Что она значит |
| ------ | ---------------------------- |
| Профиль | Профиль договора и его версия. По нему выбираются правила чтения документа |
| Стороны | Две стороны или больше. Каждая названа ключом, который за неё подписывает, и именем в Namecoin, если оно у неё есть |
| Окно | Время, которое покрывает договор, в мере своего профиля: секунды Unix в профилях версии 3, высоты блоков в версии 4 |
| Пункты | Упорядоченный список. Пункт несёт свободный текст, поля для машины или то и другое |
| Соли | Одно случайное значение на договор и одно на каждый пункт |
| Рамочный договор | Необязательная часть: идентификатор рамочного договора, под которым стоит этот договор |
| Печать | Необязательная часть: собственная печать договора |
| Выход согласия | Необязательная часть: выход, трата которого показывает согласие сторон в цепочке |
| Конфигурация | Хэш манифеста конфигурации, о которой договорились стороны. Его требует профиль договора, по которому запускается агент (глава "Доступ к агенту: команда и аренда", раздел "Слот") |

Текст пункта протокол не толкует. Текст связывает стороны, управляет работой агента и не управляет эффектом сервиса, поэтому всё, что должна сравнить машина, записано полем. Каждая сторона подписывает один и тот же идентификатор договора своим ключом, с меткой подписи, которая принадлежит только договорам. Договор заключён, когда его подписала каждая названная в нём сторона; подпись ключа, которого договор не называет, ничего не добавляет. Каким ключом подписывает сторона, определяет профиль: в профилях версии 3 выдавший подписывает ключом доверенностей, получатель своим ключом. Наименьший договор несёт только то, что нужно доверенности: стороны, окно и поля, которые повторяют доверенность. Так устроены договор доверия и условия сервиса кошелька.

Идентификатор договора вычисляется с солями. Каждый пункт входит в него хэшем от собственной соли и своих байтов, а сам идентификатор это хэш от соли договора, частей вне пунктов и хэшей пунктов по порядку. Тот, кто видит только идентификатор, не может проверить по нему угаданный текст. Чтобы раскрыть один пункт, сторона показывает его байты и соль вместе с хэшами остальных пунктов: читатель пересчитывает идентификатор и узнаёт число и места остальных пунктов, и ничего об их содержании. У раскрытия три предела. Пункт, показанный отдельно, может вводить в заблуждение, потому что его уточняет другой пункт. Части вне пунктов, в том числе стороны и окно, видны при каждом раскрытии. Сторона, которая потеряла соль пункта, раскрыть его больше не может.

Договор закрепляется в цепочке одной записью в выходе `OP_RETURN`, в формате записи выдачи, с собственным действием. Запись связана с идентификатором договора, а её указатель называет хэш сохранённых байтов подписанного договора; стороны, которые договор не публикуют, указателя не ставят. Закрепление показывает, что идентификатор существовал к блоку записи. Кто подписал, оно не показывает: это видно по подписям сторон или по трате выхода согласия. Договору, на который ссылается доверенность версии 3, собственное закрепление не нужно: хэш выдачи этой доверенности уже связан с хэшем договора. Закрепление служит договору без доверенности и рамочному договору.

Выход согласия из раздела "Произвольный договор" договор называет сам: это выход, который тратится только подписями обеих сторон и подтверждён до подписи договора. Транзакция закрепления тратит именно этот выход, и каждая подпись покрывает все её выходы. Подписи сторон под договором остаются обязательными: согласие в цепочке добавляется к ним и ни одной не заменяет. Трата показывает читателю, который не видит договора, что держатели обоих ключей подписали транзакцию с записью об этом договоре, и цепочка фиксирует время. Если сторон больше двух, выход требует подписей всех.

## Договор и доверенности под ним

Каждая доверенность ссылается ровно на один договор, пусть наименьший. Договор может существовать без единой доверенности: он заключён подписями и закреплён своей записью.

Окно доверенности лежит внутри окна договора: начинается не раньше и кончается не позже. Договор доверия требует равенства двух окон; это частный случай. Новый профиль говорит, какое из двух отношений он требует.

Профиль договора закрепляет байты одного вида договора и его привязку к доверенности. Предложение, которое вводит профиль, называет семь вещей. Первая это идентификатор профиля с версией, которая меняется при каждом изменении байтов или смысла. Вторая это канонические байты: члены и их порядок, правила кодирования и наибольший размер; читатель отказывает, если повторное кодирование разобранного значения не даёт тех же байтов. Третья это привязка к доверенности: какие члены равны её полям, как её область и пределы следуют из договора или повторяются в нём и какое отношение связывает два окна. Четвёртая, для профиля версии 3, это значения четырёх меток события согласия. Пятая это коды отказов, по одному на правило, и порядок, в котором читатель сообщает первый отказ. Шестая это проверочные наборы и программа проверки: верные договоры с точными байтами и хэшами, неверные, каждый из которых отличается от верного одним дефектом, с ожидаемым кодом, и программа, которая пересчитывает их все, с тестами, которые ловят подложенные дефекты. Седьмая это предложение, которое несёт профиль, решения, которые оно записывает, и его принятие по общему порядку предложений. Профиль, который несёт текст, говорит об этом прямо, и тогда действует правило о тексте и эффекте (глава "Сервисы по доверенности", раздел "Текст и эффект").

Рамочный договор это договор, под которым доверенности выдаются со временем. Доверенность стоит под рамочным договором, когда её собственный договор называет этот рамочный договор по идентификатору. Договор называет не больше одного рамочного договора, а рамочный договор не называет ни одного. Окно договора лежит внутри окна рамочного договора, и вместе с ним окно доверенности.

Раньше своего окна договор кончается только по машинному правилу, которое называет, кто вправе объявить конец (раздел "Договор и полномочия"). В версии 3 такое правило одно: трата печати доверенности выдавшим. Пункт, который описывает причины расторжения словами, связывает стороны и сам ничего не прекращает.

## Печать договора

У каждой доверенности своя печать, и потратить её может только выдавший. Чтобы прекратить все доверенности одного договора разом, и чтобы это могла сделать сторона, названная в договоре, договор называет собственную печать. Печать договора относится к доверенностям версии 4 и к рамочным договорам; в версии 3 выдавший тратит печать каждой доверенности.

Договор называет печать выходом: транзакцией, номером и скриптом. Выход подтверждён до подписи договора. Скрипт печати служит условием расторжения.

| Условие расторжения | Кто вправе прекратить договор | Скрипт печати |
| ------ | ---------------- | ---------------- |
| Только выдавший | Выдавший | Один ключ, выдавшего |
| Любая сторона | Каждая сторона сама | Любой из ключей двух сторон |
| Обе вместе | Стороны по согласию, ни одна в одиночку | Ключи обеих сторон |
| Арбитр | Арбитр, названный в договоре | Скрипт с ключом арбитра; точный вид задаёт профиль |

Каждая доверенность под договором требует, кроме собственных проверок, чтобы печать договора существовала с названным скриптом и не была потрачена ни в блоке, ни в мемпуле. Одна трата прекращает их все: проверяющий, который проверил трату печати договора, с этого момента отказывает каждой доверенности под договором, как отказывает доверенности, печать которой потратил выдавший.

Транзакция, которая тратит печать договора, несёт одну запись в выходе `OP_RETURN`. Запись связана с идентификатором договора и с хэшем подписанного заявления о расторжении, и её указатель называет это заявление. Заявление о расторжении подписывают те, кто прекращает договор; оно называет договор, условие расторжения и причину. Причина это свободный текст или ссылка на вердикт о нарушении. Договор прекращает сама трата. Запись добавляет свидетельство: по ней другая сторона и арбитр находят заявление. Запись, которую подписи траты не покрывают, свидетельством не служит, а договор всё равно прекращён.

У каждой доверенности остаётся собственная печать, трата которой прекращает только её. В реестре ключей у ключей печати договора средний уровень опасности: вор ключа, которому условие расторжения позволяет прекратить договор в одиночку, прекращает договор и все доверенности под ним, а полномочий не создаёт. У ключей выхода согласия уровень низкий: один ключ ничего не даёт, потому что выход требует подписей всех сторон.

## Стороны и виды договоров

От стороны протокол требует трёх вещей: ключа, который подписывает; имени, которое публикует ключ доверенностей, если сторона выдаёт доверенности; ключа или имени, если сторона доверенности получает. Чем сторона является, протокол не спрашивает. Человек, компания и агент выступают сторонами одинаково, в любом сочетании. Компания действует ключами, которые держат её должностные лица.

| Сценарий | Стороны | Договор | Доверенности под ним | Кто может прекратить |
| ------ | ------ | -------- | -------- | -------- |
| Аренда агента | Арендатор и оператор, который сдаёт агента | Договор аренды с ценой, периодом и пределами | Одна доверенность на весь срок | Выдавший, печатью доверенности |
| Доверие между агентами двух владельцев | Выдавший и агент другого владельца | Договор доверия | Одна доверенность, а с передоверием и дочерние | Выдавший, печатью доверенности |
| Услуги между двумя компаниями | Две компании | Рамочный договор на год, закреплённый записью | По доверенности на каждый заказ, каждая внутри года | Любая из компаний, если условие расторжения называет любую сторону |
| Работа по найму | Компания и человек | Рамочный договор о работе | Доверенности, по которым человек или его агент действует с ресурсами компании | Стороны вместе или арбитр, если так говорит условие расторжения |
| Соглашение без доверенности | Алиса и Боб | Договор с двумя подписями и закреплением | Ни одной | Досрочно никто: печати у него нет |

## Нотариус и арбитр

Нотариус это дополнительное звено: участник, который заверяет доверенность и может её отозвать. Нотариусом может быть агент или человек. Роль техническая; статуса государственного нотариуса у неё нет. Нотариус заверяет только то, что проверил сам, и новых прав не создаёт. Доверенностей он не выдаёт.

Главная работа нотариуса это передоверие. Агент с правом передоверия выдаёт дочернюю доверенность, и нотариус сверяет её с родительской: действия, пределы и срок, а также условия, записанные словами, которые программа не сверяет. Если дочерняя доверенность не превышает родительскую, нотариус это заверяет. Так заверяется каждая дочерняя доверенность. Правила передоверия даны в главе "Доверенность", раздел "Передоверие и дочерние доверенности". Заверять можно и другой факт, который нотариус проверил сам, например ключ получателя.

Кому доверено заверять, записано в родительской доверенности: её право передоверия называет от одного до четырёх нотариусов, и каждая строка называет одного из них. Заверяет строку только её нотариус: аттестация другого нотариуса, пусть названного в той же доверенности для другой строки, получает отказ. Корневая доверенность с правом передоверия называет нотариусов и сама заверения не требует. Каждого нотариуса право передоверия закрепляет так же, как версия 4 закрепляет выдавшего: именем `id/`, регистрацией этого имени и ключом его владельца. Ключ аттестаций нотариус публикует в значении своего имени и может сменить его обновлением имени; доверенности, которые его называют, перевыпускать не нужно. Проверяющий идёт по истории имени нотариуса и требует, чтобы значение с ключом аттестаций записал закреплённый владелец. Без закрепления новый держатель имени после передачи или новой регистрации опубликовал бы свой ключ, и его аттестации проходили бы под каждой доверенностью, которая называет этого нотариуса. Имя, у которого резервирование и первое обновление подписал кошелёк финансирования, требует одного обновления за подписью владельца имени, прежде чем родительская доверенность его назовёт. Нотариусов выбирает выдавший: именно его полномочия передоверие и ограничивает. Получатель может предложить своего нотариуса, когда стороны согласуют договор; силу предложение получает, когда выдавший подписал его в доверенности. Когда выдавший и передоверяющий принадлежат одному владельцу, заверяет нотариус выдавшего. Когда владельцы разные, заверяет третья сторона, с которой согласны оба; нотариус, который принадлежит только стороне передоверяющего, не годится.

Нотариус, названный в другом месте, проверяющему ничего не даёт. Список нотариусов в настройках подписанта служит подписанту источником для новых доверенностей, и проверяющий его не читает. Инструкции агента объясняют порядок: кому отправить просьбу о дочерней доверенности и к какому нотариусу обратиться. Имя нотариуса из сообщения или из инструкции полномочий не даёт.

Заверение устроено по одной из двух схем.

В первой схеме нотариус выдаёт отдельную аттестацию. У него своя печать. Он подписывает аттестацию с хэшем доверенности, с утверждением, которое он заверяет, и со своей печатью и закрепляет её хэш. Проверяющий, которому нужен нотариус, сверяет подпись нотариуса, его печать, закрепление и ссылку на доверенность. Каждая аттестация закрепляется своей записью в цепочке. Когда выдавший и передоверяющий принадлежат одному владельцу, печать, закрепление и работу нотариуса оплачивает выдавший; между владельцами это определяет договор.

Затем проверяющий сверяет само заверенное утверждение с тем, которого требует доверенность, право передоверия или его политика. При передоверии требуется утверждение "дочерняя не превышает родительскую" для этой дочерней доверенности, для родительской, на которую она ссылается, и для хэшей обоих договоров. Аттестация того же нотариуса о ключе получателя такого требования не выполняет, хотя её подпись, печать и закрепление верны. Не выполняет его и утверждение "дочерняя не превышает родительскую" с хэшами других договоров. Аттестация с требуемым утверждением и точными хэшами проходит, если прошли остальные проверки. Проверяющий сверяет, что именно подписал нотариус; верно ли суждение нотариуса, он не проверяет.

По предложению LIP-0014 аттестация о передоверии называет родительскую и дочернюю доверенности и хэши обоих договоров, порядковый номер дочерней доверенности и блок, который видел нотариус. Перенести такую аттестацию на другую дочернюю доверенность нельзя. Суммы по дочерним доверенностям аттестация не несёт, и проверяющий на такую сумму не полагается: пределы заданы строками родительской доверенности. Нотариус ведёт собственную запись, по одной дочерней доверенности на строку. Две аттестации одного нотариуса с одним номером для разных дочерних доверенностей сами доказывают его недобросовестность.

Нотариусом не может быть тот, кто передоверяет, и тот, кто получает дочернюю доверенность. Проверяющий сверяет то, что видно по ключам и именам: ключ нотариуса отличается от ключей обоих, а имя нотариуса отличается от имён исполнителей обеих доверенностей. Разные ключи не доказывают разных участников. Независимость обеспечивает выбор: нотариуса называет выдавший, а не тот, чьи полномочия ограничены. Владелец может сам заверять дочерние доверенности под своими доверенностями: тогда аттестация защищает его доверенности от ошибок его же агентов. В рое из главы "Рой: иерархия и полномочия" эту роль может исполнять агент независимого ревью, для доверенностей других агентов, или сам оператор; в обоих случаях под отдельным именем нотариуса.

Отзывает нотариус тратой своей печати. Если доверенность требует заверения, проверяющий допускает её только с действующей аттестацией. Нотариус тратит печать, аттестация перестаёт действовать, и проверяющий отказывает: доверенность отозвана для каждого, кто требует заверения. Печать самой доверенности при этом цела, и потратить её по-прежнему может только выдавший. Если заверение добровольное, трата печати нотариуса снимает только подтверждение, и доверенность может заверить другой нотариус.

Для дочерней доверенности действуют два правила. Проверяющий, который видел трату печати нотариуса, записывает отзыв в журнал и продолжает отказывать после реорганизации. После обычного отзыва ту же дочернюю доверенность может заверить заново нотариус её строки. После отзыва по причине заверить её заново нельзя: нужна новая дочерняя доверенность по другой строке. По предложению LIP-0014 отзыв по причине нотариус отмечает записью в транзакции, которая тратит печать, и причина считается только тогда, когда подпись самого нотариуса покрывает эту запись.

Для каждой строки нотариус ведёт одну последовательность печатей: первая аттестация строки называет её первую печать, каждая следующая называет печать той же последовательности. Поэтому одна трата по причине отзывает все аттестации строки. Проверяющий, который сам проверил такую трату на своей ноде, записывает строку закрытой по причине и отказывает каждой следующей аттестации этой строки. В версии 3 дальше правило держится на нотариусе. После отзыва по причине он обязан больше не заверять эту строку, а проверяющий, который начал работать позже и траты не видел, новую аттестацию того же нотариуса допустит. В версии 4 строка называет ещё и стоп-монету своего нотариуса: выход, подтверждённый до подписи родительской доверенности, потратить который может только нотариус. Трата стоп-монеты прекращает строку по причине для каждого проверяющего, нода которого её показывает.

Монета строки платит отдельному ключу, ключу монеты строки: подписант оператора передоверяющей стороны выводит ключ монеты строки из своего сида в отдельном счёте, тем же способом, каким подписант выводит ключи печатей. Ключ монеты строки не совпадает ни с ключом передоверия, ни с ключом сообщений. В реестре ключей у ключа монеты строки и у ключа стоп-монеты средний уровень опасности. Вор первого тратит монету вне выдачи, и по этой строке больше нельзя выдать дочернюю доверенность. Вор второго прекращает строки, и прекращённая строка остаётся прекращённой. Полномочий ни тот, ни другой не создаёт.

Во второй схеме выдача требует двух подписей:

```text
tx1  создаёт печать Алисы S_A
tx2  создаёт печать нотариуса S_N
tx3  создаёт выход M: подпись Алисы И подпись нотариуса
tx4  тратит M, обе подписи SIGHASH_ALL
     OP_RETURN связывает доверенность и заявление нотариуса

проверяющий -> подпись доверенности, S_A цела
            -> заявление нотариуса, S_N цела
            -> закрепление tx4, его вход M и оба ключа
```

Обе подписи покрывают всю транзакцию `tx4`, поэтому без нотариуса выдачи нет, и цепочка сама показывает согласие обоих с этими хэшами. Печати `S_A` и `S_N` при выдаче остаются целыми. Нотариус позже может потратить свою печать и снять подтверждение; запись о совместной выдаче остаётся, а доверенность отзывает только Алиса.

Мы предлагаем первую схему: другой нотариус подтверждает ту же доверенность без новой совместной выдачи.

Механизм описывает предложение LIP-0012: отдельная аттестация со своей печатью, подписанное требование заверения в доверенности или в праве передоверия и один добавленный шаг допуска. Поля аттестации, её закрепление, порядок проверки и коды отказов описывает предложение LIP-0014.

Арбитр это третий участник, названный в договоре. Его личность, рамки и порядок разбора записаны заранее, и своё решение он подписывает. Сторона спора арбитром быть не может. Децентрализованный суд с голосованием Swarma Link не строит: Aragon объявил о закрытии интерфейса своего суда в 2024 году, сославшись на сложность.

Силу договору даёт то, что поставлено на кон. Простейший механизм это кошелёк с тремя ключами, заказчика, исполнителя и арбитра, где для траты нужны два. Стороны, которые договорились, тратят вдвоём; в споре арбитр присоединяется к одной из них. Покрыто только то, что лежит в таком кошельке. Обязательное право от договора не исчезает: если нужна защита в суде, в договоре указывают применимое право и порядок разбора.

## Договор и полномочия

Ссылка на договор в доверенности сама ничего не отзывает. Конец договора снимает доступ, только если это условие записано в машинных правилах и названо, кто вправе о нём объявить. Отзыв доверенности, в свою очередь, не прекращает трудовых и иных отношений сторон.

Условия договора доходят до агента в рамке полномочий. Когда исполнитель допускает поручение по доверенности, его ворота допуска, то есть та часть исполнителя, которая проходит шаги проверки, передают агенту вместе с текстом поручения рамку, доступную агенту только для чтения. Рамка называет выдавшего, идентификатор доверенности, по которой поручение допущено, условия договора, то есть действия, репозитории, бюджет и окно, текст области, если он есть в договоре, и идентификатор рамочного договора, если договор его называет. Рамку ворота допуска собирают из объектов, которые проверили сами. Того, что сообщение говорит о собственном выдавшем, доверенности или условиях, в рамке нет.

Постоянные инструкции агента несут одно постоянное правило и ни одного договора. Правило говорит, что поручение другого агента считается только внутри рамки, что агент работает в её условиях и что текст области он применяет как ограничение своей работы. Условия конкретного договора в постоянные инструкции и в системный промпт не записываются. Причина в двух сроках жизни. Доверенность ворота допуска проверяют заново при каждом поручении, а постоянные инструкции загружаются при запуске агента и живут до следующего запуска. Условия, записанные в них, пережили бы потраченную печать и закрытое окно и стояли бы рядом с каждым сообщением, допущено оно или нет. Сообщение, которое дошло до агента без рамки, остаётся данными.

Рамка не заставляет агента держаться её условий: она сообщает агенту, каковы они, а эффекты ограничивают проверки исполнителя по полям.

Агент заключает договор за человека только по доверенности, которая это разрешает. Такая доверенность называет участника, от имени которого действует агент, допустимых контрагентов, шаблон или точный документ, предельную сумму и окно. Право писать агенту не даёт права подписывать договоры. Контрагент проверяет доверенность агента и хранит её в пакете договора. Доверенность показывает, от чьего имени действовал агент; юридическую ответственность определяет применимое право.
