# Namecoin как первая реализация

Доверенность от человека агенту использует в Namecoin три разных объекта: имя с ключами, выход-печать и запись об обязательстве выдачи. Они связаны подписями и хэшами, а функции у них разные.

Namecoin появился в 2011 году как первое ответвление кода Bitcoin. Его задача с самого начала совпадает с нашей: хранить имена и связанные с ними значения. Заводить собственный блокчейн для первой версии не нужно.

Защита Namecoin опирается на объединённый майнинг. Майнер Bitcoin может одновременно защищать Namecoin той же работой, без отдельного оборудования. Участвуют те майнеры Bitcoin, которые включили эту возможность, поэтому атака извне требует очень крупного майнера. У этой защиты есть оборотная сторона: добыча сосредоточена в нескольких больших пулах, то есть группах майнеров, которые работают вместе. Договорившись, они могут задерживать записи или откатывать недавние блоки. Подделать подпись владельца они не могут. Поэтому подписи защищают авторство, а подтверждение и доступность записей зависят от состояния цепочки.

## Как Алиса получает имя

Транзакция расходует прежние выходы и создаёт новые. Выход это порция монет с условием, кто может её потратить. NMC это монета Namecoin. Комиссию за включение транзакции в блок получает майнер. Имя в Namecoin живёт в особом выходе: потратить его значит обновить имя.

Регистрация идёт в два шага, чтобы никто не успел перехватить имя, увидев заявку. Первая транзакция `name_new` публикует только отпечаток имени. Через 12 блоков, в среднем около двух часов, транзакция `name_firstupdate` раскрывает само имя и его значение. После этого `name_update` обновляет значение и продлевает срок.

Выход имени содержит не меньше 0,01 NMC; в обычном примере это ровно 0,01 NMC. Эта сумма переходит от обновления к обновлению и не сгорает каждый раз, а с истечением имени пропадает. Отдельно платится комиссия. Если отправить выход на чужой адрес, имя получит новый владелец: это настоящая передача на уровне цепочки. Так спонсор отдаёт имя Алисе.

Значение имени ограничено: надёжный предел равен 520 байтам. Цепочка примет и значение побольше, но такой выход уже нельзя потратить. Имя тогда нельзя обновить, и оно умрёт в конце срока. В значении лежит короткая запись о личности Алисы и ссылка на подробный документ с адресами сервисов.

Имя живёт 36 000 блоков после последнего обновления, в среднем около 250 дней. Лёгкие клиенты перестают ему верить раньше, примерно через 222 дня, поэтому клиент напоминает о продлении примерно через 180 дней. Срок считается в блоках и не привязан к календарю. Спонсор, обещавший первый год, должен учесть первое продление: оно наступает внутри этого года. Стороны договариваются о нём сами, на доверии. После передачи подпись делает сам владелец, спонсор может дать ему только монеты.

## Пространства имён и зоны

Имя в Namecoin это произвольная строка до 255 байт. Цепочка не знает, что она значит. Приложения договорились о префиксах, то есть о части до косой черты: `d/alice` показывается как `alice.bit`, а `id/alice` означает личность. Эти два имени могут принадлежать разным людям. Консенсус не проверяет префиксы и не требует разрешения на новые.

Отсюда следуют две возможности. Можно завести своё пространство, например `swarm/alice`, и показывать его как `alice.swarm`. Правило, связывающее зону с префиксом, живёт в протоколе над цепочкой: Namecoin о нём не знает, и записи, составленные по другому правилу, наш клиент не разбирает. Такой зоны нет в корне интернет-DNS, поэтому без нашего клиента или локального разрешения она не откроется, как и `.bit`. Каждое сообщество может завести свою зону, а новая зона означает новую гонку за имена.

Вторая возможность касается поддоменов, и здесь есть ловушка. Поддомены в Namecoin живут в значении родителя: `alice.rabbit.bit` это строка внутри записи `d/rabbit`. Цепочка не выделяет поддомен в отдельную собственность, поэтому родитель может переписать его следующим обновлением. Безопасных поддоменов на уровне консенсуса в Namecoin нет. Настоящая независимость начинается с собственного имени.

## Какие ключи видит проверяющий

Профиль грантов арендодателя, описанный в LIP-0004, читает полномочия из имён `id/`. Имя Алисы хранит открытый ключ выдачи грантов, а имя Сони хранит её ключ сообщений и указатель на арендодателя. Выходами обоих имён владеют отдельные холодные ключи: их нет ни в агенте, ни в приведённых значениях.

Схема разделяет владение именем, выдачу прав и обращения к агенту:

```text
холодный ключ Алисы
  +-> выход имени id/alice -> ключ выдачи G
  +-> выход имени id/sonya -> ключ сообщений A
                              арендодатель id/alice

G -> подпись гранта -> получатель с ключом B
A -> сообщения Сони
B -> запросы в пределах выданного гранта
```

Получатель `B` может быть Бобом, который арендует Соню; ключ `A` не становится от этого его ключом. Ключ выдачи `G` также отличается от холодного ключа, управляющего именем.

В профиле значений имён с поддержкой Nostr необязательный корневой член `nostr` стоит перед `swarma`. Он содержит социальный ключ для поиска и необязательные адреса релеев. Для арендодателя социальный ключ независим от ключа выдачи грантов. Для агента он совпадает с ключом сообщений в `swarma.agent.nostr`.

Два значения ниже показаны с отступами для чтения. Обозначения в угловых скобках заменяют открытые ключи; в настоящей записи допустимый открытый ключ secp256k1 записывается 64 шестнадцатеричными знаками, а JSON записывается компактно, в порядке полей профиля. Первое значение относится к `id/alice`:

```json
{
  "nostr": {"names": {"_": "<социальный ключ Алисы>"}},
  "swarma": {"landlord": {"grant": "<ключ G>"}}
}
```

Второе значение относится к `id/sonya`:

```json
{
  "nostr": {"names": {"_": "<ключ A>"}},
  "swarma": {
    "agent": {"nostr": "<ключ A>", "landlord": "id/alice"}
  }
}
```

Без корневого `nostr` историческая форма обоих значений начинается с `swarma` и сохраняет те же полномочия. Социальное поле не добавляет права подписи грантов. При записи проверяется предел 520 байт для всего значения, включая адреса релеев, если они указаны.

Отдельная запись поиска `d/alice` связывает короткие социальные имена с ключами:

```json
{
  "nostr": {
    "names": {
      "_": "<социальный ключ Алисы>",
      "sonya": "<ключ A>"
    }
  }
}
```

Запись поиска помогает найти участника. Полномочия проверяются по именам `id/`, подписанному гранту и состоянию цепочки. Изменение одной записи `d/` не выдаёт и не отзывает грант. Если социальный ключ в зеркале устарел, поиск может привести не туда, но право на действие от этого не появляется.

## Цена и ёмкость

Размер транзакции измеряют в виртуальных байтах. Это единица веса для ограничения блоков и расчёта комиссии, она не всегда равна байту файла. Узлы пересылают неподтверждённые транзакции друг другу при ставке от 0,001 NMC за 1000 виртуальных байт. Это настройка узлов, и включения транзакции в блок она не гарантирует.

Спонсор закладывает примерно 0,012 NMC на человека: 0,01 в выходе имени и около 0,002 на комиссии. Оценка складывается из суммы в выходе имени и запаса на комиссии. При цене около 1,1 доллара за NMC в начале ноября 2026 года это примерно 1,3 цента. Запас в 15 NMC покрывает около 1250 начальных регистраций без учёта продлений. Рынок NMC тонкий, и большую закупку он не выдержит без движения цены.

Блоки ограничены: около миллиона виртуальных байт каждые десять минут в среднем, то есть примерно 144 миллиона в сутки на всю сеть. Обновление имени с большим значением в лабораторном примере занимает около 917 виртуальных байт. Миллион имён с обновлением раз в месяц заняли бы примерно пятую часть этого объёма. Для тысяч и десятков тысяч участников этого хватает. При миллионах появится очередь, и цена места вырастет. На этот случай у сети есть выход: увеличить блоки изменением консенсуса или сделать ответвление.
