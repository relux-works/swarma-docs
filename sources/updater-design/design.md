# Swarma Updater: a secure update architecture

Design note. **Proposal**, revision 7, 2026-10-27, for the owner's request of that day: a guarded updater installing only from trusted knowledge of the release, its components and hashes, whatever channel brought the first install. Trade-offs take the strong guarantee; an unsupported guarantee becomes a requirement on a named specification and a deployment gate (§6). No wire format, field, refusal code or number is introduced; the 300-second deadline is the book's (B04:285). Proposed names (Q10): `swarma-updater` and the bold defined terms.

## 1. Requirements and threat model

**Requirements.** R1: trusted knowledge only (2.2, 2.4); a download address proves nothing (IB 04:51). R2: one trust state for every delivery path (IB 04:49). R3: owner authority per effect by an operator act with explicit content (B05:107-109; 2.5); no session, keeper, updater or owner login account approves. R4: fail closed, keep knowledge, no bypass; a refusal names its step (IB 04:55, 57), rejects only the failed input and keeps the active set and durable facts; unknown outcomes fence (I:38; B22:15; 2.6). R5: no silent downgrade, freeze or mix. R6: key-loss recovery without reinstalling, given §3's quorum. R7: stop wins without the updater; only the operator's signature resumes (B05:123-131; B22:79-81; 2.7). R8: bounded resources, protected storage included (2.10).

**Attackers must not:** *CI or code host* (builds, rewrites tags, signer lists and formulas, holds CI tokens but no release key): install anything; CI identity and signer lists are not authority. *Component key:* install alone, backdate, outlive distrust. *Targets or snapshot keys below threshold* (at threshold: §3): install, add a signer, move high-water marks. *Timestamp key:* point at unsigned metadata, choose the channel; it can freeze until expiry. *Mirror, CDN, MITM:* more than denial and bounded replay within validity. *Archive, tap or `.pkg` signer:* privileged code. *Rollback, freeze, fast-forward, mix-and-match:* go below high-water marks outside a scoped exception, hide expiry, lock out a rotated host, activate what no single targets version names. *Endless data:* exhaust time, memory or protected storage, lose security state. *Updater account* (writes staging, requests preparations; may deny and lie): change installed bytes, commit metadata, move policy, mint, reuse or redirect approval, fill protected storage. *Owner login account* (`swarma update`, brew, owner-account Curator: weak point 10): approve, swap the checked bootstrap file, write the platform root. *Agents, keeper* (closed network; stop mandate): reach protected programs or approve. Host root, kernel and clock are out of scope (B04:281; A3:329-330), unreachable through updates. **Trusted:** OS, kernel and tools in the bootstrap session and check confinement; the service manager and every delegated effect owner with its fencing; distribution packages; the trusted closure; the phone key; offline key holders at threshold; the confident clock; an owner-accepted root channel's archive key (gate 1). **Excluded until gates close:** coherent whole-state restore (3), log forks shown to isolated hosts (5), malicious source signed honestly.

## 2. Architecture

**2.1 Metadata.** TUF 1.0.37 roles (Q1): *root* (all role keys, thresholds, successor; offline hardware keys, different people, Q2); *targets* (one version per **release set** of a channel, with its complete revocation state; offline, threshold, apart from component keys, Q3); *snapshot* (current targets versions; offline recommended, Q3); *timestamp* (names the current snapshot; short expiry; online narrow signer). Entries carry length, hashes and custom data (TUF §4.5) **to be defined by the platform release specification**: component identity, version, platform, use, expected signer by reference, extracted size, declared effects, service-state compatibility, closure encodings read and written, macOS Developer ID. A set selects, never introduces, a signer (I:133; IB 04:13). A **recovery publication** is a version marked recovery target. One channel in version 1; more would be delegated roles chosen by protected host policy (Q12). **Extensions** (gate 6): whole sets only; a component signature per artifact; each targets version lists every ban and distrust ever published for the channel, else is malformed; each root, snapshot and targets version has a log inclusion proof, checked before and stored with its commit. Counters follow TUF rules only (§5.3.11 included). **Policy state** (signer pins, distrusted keys, banned digests, per-component high-water marks of the highest component-signed version activated, recovery exceptions, active, previous and recovery sets with provenance, selected and retained closures) never resets on rotation; each transition makes a new **policy-state version** (gate 7).

**2.2 Component authority.** The root chain answers "in the current set?"; only a currently trusted component signer answers "these bytes as this component?", by a statement (form: release specification) binding digest to identity, version, platform and use, so a shared key (platform release key, LB) cannot cross-vouch and a signed tag binds no uploaded binary. Pins come only from the bootstrap file, not the repository signer list (IB 04:13). Planned rotation: the old key's succession statement plus an operator act naming the new fingerprint in its plan (IB 04:15), owner-checked over an independent channel; after compromise only an out-of-band owner act with an independently checked fingerprint. **Key distrust** voids all statements by a key, whatever their claimed time; an **artifact ban** voids a digest under any key; pins, distrust and bans only grow. **Install eligibility** (per check, never stored): in the current set or the act's recovery publication, unbanned, endorsed with correct bindings by a pinned undistrusted key, at or above its high-water mark. **Continuation** (active and retained recovery sets, selected and retained closures, after their accepted outcome): unbanned, each artifact keeping such an endorsement per its **provenance** in the evidence store (targets version, statements, outcome). It authorizes nothing alone: workload also needs current qualification and no stop, a recovery executor maintenance eligibility. **A successor release withdraws nothing;** only ban or distrust does (Q13). A restart between distrust and re-endorsement loses nothing; same-digest re-endorsement needs an independent rebuild reproducing it (G:137), else new digests. Software losing continuation is contained until re-endorsed or replaced. Self-update follows these rules.

**2.3 Host.** `swarma-updater`, a platform service account (I:57) networked only to release endpoints, holds no authority: its fetcher (sole network part) quarantines downloads within 2.10 bounds; its pre-verifier repeats 2.4 advisorily; its preview shows the candidate; the plan is built on the protected side. The **metadata committer**, **applier** and OS-started **boot reconciler** are fixed root one-operation programs without arguments or setuid (I:46), taking a queued identifier as untrusted hint (A3:225-227). With the verifier, loader, dependencies and the OS service definitions starting them they form the **trusted closure**, digest-pinned in a root-owned directory immutable once written (after A3:41-46); a candidate stays inert, except in the confined check, until its **closure switch**, a declared effect and the only way to change the running closure. **Trust state**, written only by protected programs: root chain, counters, log key and checkpoint, policy state, consumed identities, open operation and owning execution, pending containment records, journal.

**2.4 Acceptance and refresh.** The committer, without an act, runs the TUF client workflow (§5.3-§5.6: root versions in order at old and new thresholds, only the final root's expiry counting, §5.3.11 on rotation; snapshot and targets as named, no targets version below the trusted snapshot's; every role at threshold and unexpired), accepting a byte-identical timestamp for a cached re-check. It adds role keys pairwise distinct (B05:177), delegation per host policy, revocations containing the stored union, and an inclusion proof for each root, snapshot and targets version against a checkpoint consistent with the stored one; the timestamp, unlogged, is bounded by expiry and its logged snapshot. **Install checks**, by the applier at preparation, admission and each continuation: every artifact install-eligible and at or above its high-water mark unless the act's recovery exception covers it, platform and dependencies matching; on the protected copy, length, hashes, statement and bindings, then macOS Developer ID and notarization as defense in depth. Each role persists at its own point (TUF §5.3.8, §5.4.5, §5.5.7, §5.6.6) by synced atomic replace, a logged role with its proof and checkpoint, a targets version also with revocation union and containment records, so a root-only advance keeps its checkpoint across restart. A later failure, resource limits included, rejects only that input: accepted successors stay, the active set is unchanged, and a restart re-verifies under the same expiry rule. Unknown time refuses (A3:200-214); expiry and authority are rechecked before every commit and effect, the outcome commit included (after A3:207-209). Metadata needs no act (a root rotation is authorized by its threshold); recovery publications and revocations land without artifacts; unchanged metadata means nothing to install. A host that missed a revoking release learns it from any later version; a new host admits no platform work before its first targets commit. **Superset rule:** a version lacking a held revocation is refused, new starts close until a valid superset arrives, and gate 4 alarms (completeness over availability). **Containment hand-off:** a revocation removing continuation from active, recovery, selected or retained software, or eligibility from a prepared set, writes a pending containment record in the same atomic step, synced before the refresh is acknowledged; the admission owner reads these first at boot and resends notifications without waiting on them; merely omitting the active set writes none. **Freeze alarm:** a protected observer outside the updater account compares expiry with confident time and alarms the owner (gate 4; A3:344-352).

**2.5 Approval.** The protected side builds the plan (components, versions, digests, signer changes, all declared effects including a closure switch, services, window) and its digest from the prepared set and trust state, never the preview. The **act** binds host, kind (install, recovery, migration, disposition, closure recovery), prior state (active set, policy-state version; for a takeover the operation and the state re-observed behind its fence), target set, plan digest (a disposition's replacement plan: remaining effects, prior identities, or recovery), window and single-use identity; timestamp refreshes do not void it. Bytes and a phone showing exactly what it signs: operator path specification (B05:109; gate 2). **Current checks:** phone key pinned and unrevoked (B05:115); no global stop or pending containment for the target; window open under confident time; metadata current; the install checks (2.4). Stale authorizations never execute (B22:35). **First admission**, once, at intent: identity unconsumed, no **open operation**, prior state equal; the applier binds the identity to this operation and records it as the host's only open operation, with act, plan digest and itself as first **execution**; never reapplied after an unknown outcome (B22:15). **Continuation**, at the mutation boundary and before each effect, asks whether the identity is bound to this operation, not whether it is unconsumed: current checks; this operation's act and plan digest; the caller is its owning execution; the journal expects this step; the policy-state version moved only by this operation's journaled transitions (set pointer, closure switch, recovery exception), so any other change, an unrelated metadata commit included, refuses (accepted availability cost). The open operation is a durable record, not a lock, reserving the update scope through window exchange, service waits and qualification outside the serialization point. Until it ends only a disposition or closure recovery act naming it and its observed state is admitted (**takeover**); the earlier act never continues. A takeover issues nothing before the replaced execution's fence is complete (2.6) and refuses at first continuation unless the re-observed identities still match. Stop, containment and metadata commits never wait on an operation.

**2.6 Transaction.** The applier opens staged files without following links, copies them into a root-owned immutable evidence store hashing what it writes, and verifies, extracts and installs only that copy, into a new root-owned set directory within the declared size; absolute paths, parent references, escaping links, devices and unexpected owners or modes refuse. **Declared effects** (set directory, active pointer, closure switch, units, launch configuration, `sudoers`, firewall rows, reversible migrations) name target, prior and new identity and **delegated effect owners**, processes outside the applier's tree that run its work, such as the service manager's queued jobs (systemd, Sources); anything undeclared refuses. One serialization point (bounded local checks and durable writes only; after A3:285-289) orders admission, continuations, effect records and metadata commits. Each effect has a synced *started* record before it, naming delegated work its owner can name before handover (else the fence covers that owner's work on every target), and its observed identity (new, prior, other) after; started without disposition is **pending**.

An **execution** is one run of a protected program for the open operation, the journal naming the owner; ownership passes only at intent, admitted takeover and closure handoff. Stop, containment, takeover, restart or handoff **retires** an execution for good; restarted programs and competing invocations own nothing and fail continuation. The **operation fence** (recorded at intent, kept to the end; mechanism per platform: gate 7) covers each execution's tree and descendants, **reactivation sources** (restart policy, timers, socket, path, boot triggers) and all delegated work. A retired execution's fence is **complete** only with its tree confirmed absent, reactivation closed, each delegated item resolved (finished, result observed) or fenced (cancelled with confirmed absence, or its owner prevented from running it), and targets re-observed under continuous exclusion held to a terminal disposition; cancellation, timeout, main-process exit, unit success, a released lock or an absent requester prove nothing (A3:314-317). **The owner's own live tree and delegated work are recorded, not an overlap:** it proceeds under continuation, while no other execution (takeover, disposition, recovery, retry, closure successor) issues an effect before every retired execution's fence is complete; fencing and observation are not effects. An incomplete fence keeps the operation interrupted, admission closed, the alarm raised and dispositions refused, and never counts as containment.

**Phases,** each synced (after A3:291-303; gate 7): *prepared* (copy verified, plan digest); *intent* (admission, first execution, effects, fence); *window* (admission closed, stops confirmed, continuation: the mutation boundary); *effects* in plan order under continuation, a closure change checking the candidate first and switching last; **closure handoff:** the outgoing execution retires at the switch, and the selected closure's execution owns the operation only after the outgoing fence completes (replaced programs absent, unstartable by their boot definition) and the state is re-observed, comparing identities at its first continuation; *qualification*, a fresh signed attestation covering the selected closure's programs, dependencies and boot definition (I:103-105; B04:273-274); *final check* under serialization (after A3:262-267): closure, pointer, units and inputs as attested, every effect observed new, no delegated work outstanding, current checks passing, no stop or containment; then the **accepted outcome**, else refusal, admission closed. Only that outcome or a refusal before any started record is terminal; anything else is **interrupted**, its pending effects open across restarts; only an accepted outcome admits (A3:305-308). The **boot reconciler** completes each open operation's fence first (a restart ends the tree, not work re-queued at boot or reactivation sources the operation installed), then observes started effects, replaying nothing, admission closed; an interrupted record settles nothing. The owner disposes by an act bound to operation, re-observed state and replacement plan (remaining effects, prior identities, or recovery); the operation ends when every effect has a disposition and the result passes fresh qualification and final check, its outcome describing that state (stricter than IB 05:15; A3:305-313: recheck, requalify, never infer success or restore an old pin over changed files). Irreversible migrations are separate "migration" operations (own act, window, effects, qualification, outcome) after a completed install, so recovery to the predecessor stays possible until then. A coherent old whole-state image passes local checks (A3:329-330); refresh restores counters and revocations; consumed acts and journal need an external non-rollback anchor (gate 3): not claimed.

**2.7 Admission, stop, containment.** For the window the admission owner closes new starts, the operator signs the "blocked for update" fence record (refused from agent sessions, IB 05:9), and services stop with confirmed outcome, an unknown one postponing (IB 05:11). **Stop** state is durable, read by new binaries at start and carried through every switch, restart (B05:131) and in-flight effect, or the applier refuses. A stop waits for no effect and no late effect undoes it: *immediate denial* closes admission, starts, resumes, credential issuance and new credential uses, retires the owning execution and applies the stop handlers' restrictive settings (B05:123-131); *completion* completes the fence (2.6), turns the in-flight effect pending, and reapplies and re-observes the settings under continuous exclusion. Only then is a stop or containment **complete**, so nothing the operation started or handed to the service manager lands afterwards; with no open operation, once its settings apply (gates 4, 7). **Containment:** a ban or lost continuation in the active set or selected closure is a qualification revocation (B04:285): starts, resumes and issuance close at once, and the credential gateway and action service close new uses for the tuple, so earlier leases serve no new request (B11:146); running work is verifiably narrowed or stopped, absence confirmed, within 300 seconds of detection on Linux and macOS stations; a failed notification neither reopens nor delays, and a missed deadline fails qualification even with fences closed (B04:285-287). After a global stop gateway and action service reopen only through their closed reopening (B22:79). The admission owner owns the response, the protected side records and signals it (A3:354-365). A contained closure does no protected operation after the recording commit; a maintenance-eligible predecessor or a re-bootstrap keeping trust state recovers it. **Reopening** is the admission owner's own decision (A3:272-277), not the applier's or qualification's: no open operation, the last accepted or refused before any effect; a fresh attestation (IB 05:9) bound to the selected closure and made after the last effect, none predating a binary replacement, failed check or drift (B04:277); no global stop, pending containment, revocation touching the active set or other fence.

**2.8 Recovery and closure change.** Recovery is forward: a "recovery" act applies a recovery publication naming earlier artifacts; counters advance; previous copies and provenance stay. Its **recovery exception** (its own journaled transition, bound to the act's identity and the exact digests) passes the high-water check only for those artifacts while that set stays active, ending unreusable when another set activates; any other lower version needs its own publication and act; bans, distrust and containment apply. **Maintenance eligibility**, separate from workload admission, lets a **recovery executor** (the selected closure before a switch, the retained predecessor through its independent entry after one) run bounded protected maintenance on an unqualified installation without admitting workload or using any attestation, none surviving a binary replacement, failed check or drift (IB 05:9; B04:277). At entry and before each effect it needs: *integrity* (programs, dependencies and boot definition, re-hashed from the immutable directory, equal its provenance); *current trust* (continuation under the current trust state's revocations, never its own older copy); *readability* (every trust-state and journal record, later closures' included, interpreted before the first effect; an unknown one refuses, toward re-bootstrap); an admitted recovery or closure recovery *act* passing continuation; *no stop* (no global stop, whose lifting is the operator's signed act and reopens nothing, B05:123-131; no pending containment of executor or target); *exclusion* (one executor; every retired execution's fence complete, the replaced closure's programs included; admission closed, fence held). It ends like any operation, with qualification of the then-selected closure and the admission owner's reopening; bans, distrust, consumed identities, revocations and journal records are never erased.

Before a switch the selected closure's boot reconciler, started from a root-owned definition only a switch changes, holds admission closed while its applier and committer take the recovery act and current recovery publication; a candidate that cannot start or read metadata never touches this path. **Confined check:** the selected closure runs the candidate under OS confinement (read-only copies of trust state and journal, no protected or helper write path, no network, descendants confined) and compares protected-store identities before and after; it passes only if the candidate reads both copies and reconciles without effect and the selected closure reads back every encoding the candidate writes to scratch; a write attempt fails it harmlessly; a check-mode argument is not confinement (gate 7). The **switch** is the last effect, continued at the actual pointer change, then the handoff; qualification and final check bind the selected closure, never the earlier attestation. **Backward readability:** until the next switch's accepted outcome, protected state (trust state, consumed identities, revocations, journal) is written only in encodings the predecessor interprets with the same meaning; a new encoding takes two closure releases (read, then write); entries declare encodings; the scratch read-back is evidence, not proof, so entry rechecks; unreadable state is a failure toward re-bootstrap. **Independent entry:** predecessor and boot definition stay installed and inactive; it starts only via the operator path (B05:109) or the 2.9 session, never automatically (IB 05:15), holds admission closed, runs under maintenance eligibility, accepts only a closure recovery act naming the open or last operation, re-observed state and replacement plan, and switches back as its qualified last effect. No other closure change while a switch lacks an outcome; generations retained after failed switches or recoveries: gate 7. Sets declare per-service state versions read and written, apart from protected encodings; recovery refuses unreadable service state. **Failed qualification** keeps the new set, admission closed, until the owner decides (IB 05:15; I:155); recovery runs under maintenance eligibility; workload only after fresh qualification. Pre-published recovery publications: Q7.

**2.9 Bootstrap and channels.** *Invariant:* the bytes the owner's digest comparison authenticates are those every privileged consumer reads, and nothing outside the trusted base changes them or the session's display in between; a root fingerprint authenticates root material, not the checker. *Procedure* (gate 7): an OS-started administrator session the owner's login account cannot influence (absolute-path OS tools, nothing from the owner's environment, password never typed in the owner's session); a root-run OS tool copies the download, links unfollowed, into a new root-only directory, no other handle open, and hashes it for the owner to compare with root-chain-signed metadata shown over the fingerprint's independent channel (I:17); the OS installer gets only that path, root-only until all its steps end; local-file install, dependencies only from the distribution archive. The checked file holds installer, helpers, root version 1, signer pins and log key; other packages' triggers are trusted base. No install-time code: privileged steps run only from the checked installer under the approved plan, password once (I:83). *Channels:* `.deb`, `.rpm`; `swarma.pkg` with Gatekeeper and notarization as defense in depth; Homebrew runs tap code before any check, so no full-install bootstrap (Curator-only possible, Q9). **No root-run package manager after installation zero:** maintainer scripts and `%pretrans`/`%pre` run before unpacking with root privilege (Debian Policy §6.1; rpm-scriptlets(7)), and apt fails to a compromised archive key (apt-secure). No Relux source stays configured for platform packages; the package's later state (removal or hold, so no package operation replaces platform files): gate 7; later bytes only via the updater, no admin password. A kept root channel puts its archive key in the trusted base: per-host authenticated owner decision (gate 1). OS packages' effect is A3's subject, excluding malicious archives (A3:327-331). Untrusted Homebrew prefix writers void guarantees; services never run from the prefix. Never `CURATOR_INSTALL_INSECURE_SKIP_VERIFY` (IB 04:57; removal open, G:148).

**2.10 Resources.** Per-input bounds: object size, bytes per refresh, roots walked, entries, signatures, delegations, extracted size and ratio, retries, progress time per mirror and attempt; signed lengths only tighten; unauthenticated lengths stay within fixed caps (A3:17-21, 155); failover past the progress bound. Each protected store (trust state, journal, stop state, containment records, evidence store, prepared sets, retained closures) is bounded, with a security-record reserve preparation cannot use. Preparation starts only if declared sizes fit; over-length copies stop; past a bound on unapproved prepared sets the oldest goes and acts naming it fail admission; bytes equal to active or recovery copies are referenced. Cleanup spares active and recovery sets and provenance, selected and retained closures, revocations, open operations and identities whose window is open under confident time. Saturation refuses explicitly (A3:301-303). Values: gate 6; compaction: gate 7. Network denial blocks updates and, under Q6, new starts after expiry.

## 3. Pins, rotation, transparency

**Pins** (source; sole change authority): root version 1 (checked bootstrap file, owner-checked fingerprint; successors at old and new thresholds); role keys (the root; the trusted root); component signer pins (bootstrap file; 2.2 only: succession statement plus operator act, after compromise the out-of-band owner act; root metadata or a log-key change alone adds none); log key (bootstrap file; a root-chain-authorized statement, gate 5); channel (host policy; an operator act); Developer ID (set entry; the targets role). **Rotation:** rotating timestamp or snapshot keys deletes the trusted timestamp and snapshot (TUF §5.3.11), and targets rollback compares against the trusted snapshot (§5.5.5), so inflated targets references, delegated included, vanish. **A targets-key compromise is recovered by a new root rotating targets, snapshot and timestamp keys together;** no Swarma counter reset. Old-key replay fails, as the keys left the root and root versions never go back; policy state is untouched; cached targets files are re-verified. After any role compromise the targets role bans or distrusts what the stolen key signed, and the log shows submitted versions; a stolen threshold's ban is permanent, an availability loss fixed with new bytes. In-band root recovery needs a usable threshold of trusted root keys the attacker lacks, which loss alone can break; otherwise owners re-pin out of band, keeping policy state and history. **Transparency:** a pinned log key; checkpoints it signed, consistent with the stored one (as go does for `sum.golang.org`); inclusion per 2.4; a checkpoint older than a bound **to be defined** refuses commits. The log shows only what was submitted to the log this host sees; versions missing from it are refused. Split views need cosigning witnesses or comparing monitors, and someone must watch for unsigned versions (gate 5; placement Q4). The platform rollback witness sits on the owner's trust node (B29:199) but is not served (B29:200; W:4-6) and verifies only keyholder records (W:7-8), so it is not the release log; a public log such as Rekor is the alternative.

## 6. Gates and owner questions

A gate is a guarantee this design requires but cannot claim until its contract exists. **Each gate blocks deployment;** no waiver is offered, and a weaker deployment would need an explicit, authenticated, recorded owner decision, which is not recommended. (1) **Root-run package channel** only by authenticated owner acceptance per host. (2) **Operator act:** bytes, act kinds, display guarantee. (3) **Non-rollback anchor** against whole-state restore, e.g. the served rollback witness with a binding only its specification owner can define. (4) **Freeze alarm and stop ordering:** the protected observer and its delivery (2.4); immediate denial, then the complete fence before stop or containment counts as complete, an incomplete fence reported as unresolved interruption (2.6, 2.7). (5) **Log authority:** key bootstrap and rotation, checkpoint freshness, cosigning witnesses or cross-observer comparison, a named monitor (§3).
