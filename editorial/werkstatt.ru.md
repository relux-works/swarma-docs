# Werkstatt: постоянные рабочие места агентов

Рабочая записка от 18 октября 2026 года. Здесь решения Ивана, найденные дыры с хозяевами и результаты пилота. Записка нужна, чтобы ничего не потерялось, пока у доски нет своего оркестратора, то есть до конца выезда с agents-infra. Решения отсюда потом переходят в спеки (CIP-0002 и спеку доски) и в книгу.

## 1. Что такое Werkstatt

**Werkstatt** (по-русски «верстак») — это связка «проект × роль (профиль) × среда».

У каждого верстака есть:
- свой управляемый дом Curator;
- свой клон репозитория;
- своя личность в Matrix, например `ivmbp_memory_dev1`.

Личность, дом и память у верстака постоянные. Контекст сессии свежий на каждую задачу.

Как устроена работа:
- Оркестратор проекта ведёт доску и раздаёт задачи верстакам сообщениями в комнатах. Разработчики сдают работу. Ревьюверы в репозиторий не пишут, а вердикты пишут на доску.
- Эфемерные спавны остаются для разовых задач.
- Оркестратор со временем сам становится верстаком: Иван и Алексей говорят с ним через Matrix, а чат сессии остаётся техническим root-каналом.

## 2. Решения Ивана (18 октября)

| Тема | Решение |
| --- | --- |
| Рабочая копия | Отдельный клон на верстак, не worktree. Worktree делит с основным чекаутом базу объектов, ветки, хуки и блокировки. |
| Где лежат клоны | Отдельный корень, например `~/Werkstatt/<верстак>/`, без `CLAUDE.md` и `AGENTS.md` выше по дереву. **Почему:** Claude ищет `CLAUDE.md` от рабочей папки вверх до корня диска, и подмена `HOME` или `CLAUDE_CONFIG_DIR` этот подъём не останавливает. Записать в спеку. |
| Каталог git | Рядом с рабочим деревом, а не внутри: `git clone --separate-git-dir`; пути передаются через `GIT_DIR` и `GIT_WORK_TREE`. **Почему:** песочница Codex (workspace-write) закрывает любую `.git` внутри разрешённых корней, и в обычном клоне разработчик не может ни fetch, ни commit. Найдено в пилоте. |
| Контекст | Свежий на каждую задачу. Доработка после ревью продолжает тот же тред. Родная память агентской среды включается только явным флагом. Режимы: пересоздать сессию с той же личностью или сжать контекст штатно. |
| Доставка задач | Сообщениями в комнатах со звонком a2a, через root-канал — никогда. |
| Доверие | Пока простое: верстак берёт задачи и команды только от личности своего оркестратора в своей комнате, остальное считает информацией. Право на задачу даёт запись на доске. Позже доверие будет держаться на подписанных грантах. |
| Независимость ревью | Проверяется по личности: продьюсер и ревьювер — разные личности, оркестратор не ревьюит. |
| Логин Claude | setup-token, один токен на все дома. Remote Control верстакам не нужен: есть Matrix и гранты. |
| Скиллы и `AGENTS.md` из репозитория | Curator проверяет их и запускает **без ручного одобрения**, если проверка чистая. Проблемные части выбрасывает из запуска и пишет в журнал, который в идеале может прочитать сама сессия. Харнес сам их не находит, потому что дерево верстака sparse. |
| Права агентской среды | Все права ведём сами и программно: Curator собирает их из профиля верстака и грантов, агент меняет их по грантам. Права из репозитория не действуют. Сейчас все наши запуски идут без песочницы. |
| Родная память харнесов | Выключена по умолчанию, включается параметром. |
| Поколения | Живую сессию не трогаем, новые сессии получают новое поколение. |
| PATH | Скиллы и их CLI ставятся на верстак. |
| Агентские среды | Первыми Claude и Codex; Muse — если влезет. |
| Чужой кандидат | Ревьювер получает его как инертный дифф. |
| Ядро корневого контекста | Lean core: только универсальное, остальное — оверлеями, кому что нужно. Делаем во время выезда. |
| Git-сервер проекта | gitolite на машине проекта:<br>• каждый верстак пушит только в свои ветки `werkstatt/<id>/*` своим ключом, и это должно быть гарантировано;<br>• `main` двигает только служба доставки;<br>• рядом отдельный репозиторий доски;<br>• GitHub остаётся зеркалом для публикации и CI.<br>Потом — отдельный аудит, что gitolite нельзя обойти. |
| Реестр верстаков | Элемент доски `station` с описанием запуска: среда, модель, профиль, клон, личность. `station up <id>` поднимает сессию по записи, `assign` отдаёт задачу. |
| Роутер (cmr) | Две функции: выбор модели для верстака при создании или перезапуске (смотрит на недельный запас квоты) и выбор верстака под задачу. Сначала фильтры, потом качество, загрузка и цена. Если подходящего нет, роутер отказывает. Есть теневой режим. Effort выбирается на каждую задачу при запуске. Место cmr в платформе пока не решено. |
| Общий дом конфигов роя | Предложение, на решении Ивана:<br>• `~/.config/swarma/<элемент>/` — то, что правит человек;<br>• `~/.local/state/swarma/` — состояние;<br>• `/etc/swarma/` — системный слой для агентов со своими пользователями ОС;<br>• настройки верстака — в его записи в реестре;<br>• Curator остаётся в `~/.curator`, перенос — только через CIP. |
| Каналы владельца | Matrix, почта, Telegram. Начинать с каналов, где сообщение можно подписать, а оркестратор проверяет подпись. |
