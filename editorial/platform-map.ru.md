# Карта платформы Swarma: продукты, модули, репозитории

Рабочая записка оркестратора, версия 2 от 18 октября 2026, после ответов владельца. Это предложение. Решения владельца отмечены отдельно, остальное ждёт его подтверждения. Основа — дизайн книги и инвентарь репозиториев relux-works на 18 октября 2026.

## Решения владельца (18 октября 2026)

- Слой называется **Swarma Runtime** — не Swarm Runtime и не Swarm Agents Runtime.
- Curator становится **Swarma Curator** и входит в Swarma Runtime.
- Привилегированные службы живут в отдельных маленьких репозиториях. Это обязательно.
- Для каждого модуля и элемента нужны имя, место в платформе и репозиторий. Это касается A2A, доски, реестра владельца, библиотеки форматов, дистрибуции, стороны донора и iOS-приложения.

## Семейство имён (предложение)

Платформа — **Swarma**. Предлагаю одну схему «Swarma ‹имя›» для всего семейства:

| Уровень | Имена |
| --- | --- |
| Слои | Swarma Runtime, Swarma Protocol, Swarma Chain |
| Продукт поверх цепочки | Swarma Social |
| Модули рантайма | Swarma Keyholder, Swarma Registry, Swarma Broker, Swarma Operator, Swarma User Manager, Swarma Dispatcher, Swarma Session Host, Swarma Network, Swarma Workplace, Swarma Curator, Swarma Keeper, Swarma Courier, Swarma Board, Swarma Delivery, Swarma Memory, Swarma Router, Swarma Inference, Swarma Donor |
| Общее | Swarma Formats, Swarma Spec, Swarma Docs |

Как называть репозитории и программы:

- Внутри новой организации у репозиториев короткие имена: `dispatcher`, `keyholder`. Пространство имён даёт сама организация.
- У бинарников служб префикс `swarma-`, чтобы они не сталкивались в PATH.
- Инструменты агентов и людей носят короткие имена: `curator`, `board`, `memory`, `cmr`, `courier`.
- По-русски модули называются как в книге: ключник, реестр владельца, брокер, хост сессий и так далее.

## Swarma Runtime — набор служб, а не один процесс

Отдельного процесса «runtime» нет. Рантайм — это службы под разными пользователями ОС, с разными правами и границами. Вместе они дают рою работать на машинах владельца. Модули ниже сгруппированы по назначению.

## Ответы на вопросы владельца

### Почему всё лежит в curator-spec

Исторически `curator-spec` оказался единственным репозиторием спек с процессом предложений, поэтому туда шли предложения всей платформы. Например:

- CIP-0008 — режим удалённого работника;
- CIP-0009 — сторона донора и мост;
- CIP-0011 — брокер и учётки агентов.

Ответственность за них при этом не Curator. Мост донора — это Swarma Donor и Swarma Workplace, брокер — это Swarma Broker. Предложение: в новой организации у платформы своя спека, Swarma Spec, с предложениями SIP. Предложения не про Curator переезжают туда, а `curator-spec` остаётся спекой Curator.

### Когда писать протокол моста донора (`swarma-rb/1`)

Он нужен для этапа внешних доноров. В «Ближайшем пути Runtime» этот этап идёт после защищённого пути на одной машине: менеджер пользователей, диспетчер, брокер, хост сессий, оператор. Протокол стоит начинать за одну-две недели до того, как начнём реализацию Swarma Workplace и Swarma Donor. Если первый внешний донор нужен раньше, протокол поднимается в очереди вместе с этим этапом.

### Два «моста»

В книге словом «мост» названы две разные вещи:

- мост сообщений из главы 7 — это Swarma Courier;
- мост донора из главы 12 — часть Swarma Donor.

Предложение — развести имена: «курьер» для сообщений и «мост донора» только для стороны донора.

### Почему Courier, а не A2A

«A2A» уже занято: Agent2Agent — открытый протокол, начатый Google и переданный в Linux Foundation. Если назвать модуль так же, будет путаница, а взаимодействовать с тем A2A мы, возможно, захотим: курьер может принять его как ещё один носитель. Поэтому предлагается **Swarma Courier**, а CLI `a2a` живёт как псевдоним на время переезда.

### Доска

**Swarma Board** — задачи, роли, плейбуки, ядро процесса и Change Request. Из нынешнего `skill-project-management` модули расходятся так:

| Сейчас | Куда |
| --- | --- |
| Доска, ядро процесса, плейбуки, роли, Change Request, worktree-поток | Swarma Board |
| `tb-sessiond`, Session Manager | Swarma Session Host |
| Запуск дочерних исполнений (`spawn`) | Заявки в Swarma Dispatcher; доска остаётся заказчиком |
| Цели: постановка, подталкивание, предложение «готово» | Интерфейс целей Swarma Session Host; доска публикует цели как необязательный клиент |
| Обязательства («кто кому что должен и к какому сроку») | Swarma Keeper |
| Приземление и публикация | Swarma Delivery |
| Скилл (`SKILL.md`, роли) | Пакет, который ставит Swarma Curator |

### Контроль целей (поправка к прошлому ответу)

Сегодня цели — механизм доски. Сессия получает цель (`task-board goal set-primary`), демон доски подталкивает её к цели, а когда агент предлагает «готово», исход проверяется отдельно. По книге (глава «Запуск агента и хост сессий», раздел «Цель не принадлежит агенту») интерфейс целей переходит в **хост сессий**:

- цель ставит вызывающий или доска;
- служба проверяет полномочие на сессию и передаёт ревизию цели раннеру;
- бюджет подталкиваний задаёт грант;
- предложение «готово» уходит тому, кто поставил цель.

Swarma Keeper отвечает за другое — за обязательства и эскалацию. В прошлом ответе цели ошибочно отнесены к Keeper.

### Три поколения хоста сессий

Хост сессий за осень проектировали три раза в разных репозиториях:

| Репозиторий | Что в нём |
| --- | --- |
| `agent-session-manager` | Реализация менеджера сессий, к 1 октября |
| `agent-session-host` | Дизайн хоста, 27 сентября |
| `platform/swarma-session-host` | Спека в составе платформенных служб, 13 октября |

Плюс работающий сегодня `tb-sessiond` внутри доски. Это один модуль, и в новой организации от него остаётся один репозиторий, `session-host`.

### История при переезде

| Способ | Плюсы | Минусы | Где применять |
| --- | --- | --- | --- |
| Перенос репозитория средствами GitHub | Сохраняются история, подписи, issues, звёзды; старые ссылки перенаправляются | Переезжает вся история, в том числе лишнее | Уже публичные и проверенные: `curator`, `curator-spec` |
| Новый репозиторий из проверенного снимка: один подписанный начальный коммит с записью происхождения (исходный репозиторий и ревизия) | Чисто, ничего лишнего из старой истории; проверять нужно только снимок | Подробная история остаётся в приватном архиве | Приватные рабочие репозитории с богатой историей |
| Переписывание истории с переподписью | История сохраняется | Нужно проверить каждый старый коммит на секреты, личные пути и имена; все хэши меняются, и ссылки из досок и спек всё равно ломаются | Только если история нужна публично и её реально проверить |

### Привилегированные службы

Своё маленькое репо получают ключник, реестр, брокер, менеджер пользователей, диспетчер, сеть (правила ядра) и служба приземления. Их легче аудировать, и у каждой своя граница выпуска.

## Что решить владельцу

1. Схема «Swarma ‹имя›» для всего семейства: Swarma Protocol, Swarma Chain, Swarma Social, Swarma Keeper и остальные модули.
2. Имена модулей из карты: Keyholder, Registry, Broker, Operator, Courier, Board, Delivery, Donor, Formats, Spec, Runtime.
3. Имя организации на GitHub.
4. Где живут спеки: отдельная Swarma Spec с SIP, а `curator-spec` только для Curator.
5. Способ переезда по каждой группе репозиториев (таблица выше).
6. Порядок переезда. Предложение: сначала то, что уже работает и нужно каждый день (Curator, доска, курьер, роутер), затем службы рантайма по мере реализации.
