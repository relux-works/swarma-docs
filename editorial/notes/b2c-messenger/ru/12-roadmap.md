# После хакатона: продукт и решения

Хакатон проверяет две вещи: понимает ли человек узкое разрешение и получает ли он полезный ответ. Настоящему продукту нужна надёжность и повторяемые гарантии на реальных устройствах, а не больше экранов. Ниже — порядок работ, который мы предлагаем вернуть в дорожную карту платформы. ⟦предложено⟧

| Следующий результат | Что получает платформа |
| --- | --- |
| Ядро Signer и работа с ключами устройства | Общие тестовые векторы подписанных сообщений, проверка отмены и точных байтов, утверждённый язык ядра |
| Провайдер XMPP в a2a | Контракт адресов, адресатов, повторов и квитанций; проверка на двух доменах и при смене устройств OMEMO |
| Автоматическое создание помощников | Учётка, ключ, аккаунт, профиль и сессия создаются одной операцией с откатом при сбое |
| Потеря устройства без потери контроля | Резерв корня, отзыв входа и шифрования, свежесть и защита реестра от отката, работа офлайн |
| Нормальный мобильный цикл | Push без текста, работа в фоне, переподключение, перенос ключей шифрования, история без потери границ |
| Безопасные инструменты между владельцами | Узкие API данных вместо доступа модели ко всему; тесты границ и аудит без лишнего содержимого |
| Агенты на разных станциях | Контракты сессий и запуска, явное владение и остановка; логины к моделям остаются только у брокера |

Готовность подтверждают сквозные испытания: разрешённый семейный запрос проходит, а расширение прав, повтор, отмена и отзыв ничего не меняют. Для каждого нового правила допуска нужен тест, который убирает именно это правило и показывает, что запрещённое тогда проходит. Две реализации, которые одинаково ошибаются, — не доказательство правильности.
