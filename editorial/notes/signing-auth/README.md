# Подписи и аутентификация в Swarma

Короткая русская записка для оператора и команды: утверждённая архитектура
Swarm Signer, а не заявление о готовности всех компонентов.
Готовый документ: [signing-auth.ru.pdf](signing-auth.ru.pdf).

## План и основания

Порядок глав: проблема A0 → ключи и цепочка → телефон → Element → агент →
новое/потерянное устройство → отказы → конверт → федерация → уверенность и
гранты → устройство Signer и открытые решения.

| Основание | Что из него взято |
| --- | --- |
| Книга «Swarma» 1.2, ревизия `dac2201adb3e956685cd67d5c5cf10c04986401d`, главы «Ключи и ключник», «Гранты и полномочия», «Путь сообщения и мост» | отсутствие закрытого ключа у агента; UID и поколение; ослабление грантов; A0–A3; переходный режим; канал владельца; данные коллеги и человеческое распоряжение |
| Та же книга, главы «Допуск к носителю», «Идентичность агента» | закреплённая подписанная ревизия реестра, git-аудит, отдельные корни, снимки до 60 секунд и предел защиты от раздвоения истории |
| Утверждённая схема Signer от 23–24 октября 2026 года | FIDO-корень; root-аттестации; key provider; Matrix/OMEMO; `swarm-envelope/2`, CCJ-1 и перечисленные поля; namespace `swarma-msg`; направления Seraph/A2A/Signer/Keymaker |
| Уточнение схемы Signer от 24 октября 2026 года и план Seraph S0 | Secure Enclave P-256/ECDSA; FIDO по модели; агентский Ed25519; совместимость Ed25519/P-256 low-S, алгоритм в аттестации; точная ASCII-метка без `0x0a` и управляющих байтов + `0x0a` + CCJ-1; попарно различные метки из закрытого списка, побайтное сравнение до первого `0x0a` без нормализации, разделение ролей/доменов; рекомендация Rust/UniFFI с Matrix Rust SDK остаётся на ревью |
| `editorial/style.ru.md`, `names.ru.md`, `sources.ru.md` | голос, терминология и старшинство источников; русский текст — источник правды |

Схема Signer уточняет оперативную иерархию ключей и дополняет книгу. Она
не переопределяет формат ячеек Swarm Chain. Связь аппаратного FIDO-корня
с долгоживущими корнями книги оставлена открытой. Материал не добавляет
новых полей, алгоритмов или нормативных кодов отказа. JSON — иллюстрация,
не conformance vector; SHA-256 тела настоящий, подпись — явная заглушка.
Неопределённые детали перечислены в [UNRESOLVED_QUESTIONS.md](UNRESOLVED_QUESTIONS.md)
и в последней главе PDF.

Путь подписи устройства сверяется с документацией Apple
[SecureEnclave.P256.Signing](https://developer.apple.com/documentation/cryptokit/secureenclave/p256/signing):
это P-256/ECDSA. В этом пути Secure Enclave ключа Ed25519 нет. Поддержка FIDO
зависит от модели; Seraph S0 описан как план совместимости, не как проверенная
реализация. Кодировка подписи и вывод идентификатора ключа остаются открытыми,
отдельно от уже заданных алгоритмов и правила доменной метки.
Разделитель `0x0a` различает подписываемые представления разных допустимых
меток, даже если одна — префикс другой; запрет префиксов для безопасности не нужен.

## Сборка

Используется исходный checkout публичного скилла `relux-works/skill-platform-book`
на **`1c75fdf4a09960e41ea153645da7c48800b7a82b`**. В переменную `BOOK_SKILL`
передаётся каталог этого checkout. Перед запуском проверить:

```sh
test "$(git -C "$BOOK_SKILL" rev-parse HEAD)" = 1c75fdf4a09960e41ea153645da7c48800b7a82b
```

Команды выполняются из корня документационного репозитория в обычном
активированном venv Python 3.12.15 с пакетами из
`$BOOK_SKILL/requirements-lock.txt`. Pandoc 3.11 и нативные библиотеки WeasyPrint
должны быть подготовлены отдельно, по README скилла. На macOS при необходимости
задаётся `PLATFORM_BOOK_LIBRARY_PATH` с каталогом нативных библиотек.
Сборщик не устанавливает зависимости. PDF основной книги эти команды не меняют.

```sh
NOTE=editorial/notes/signing-auth
"$BOOK_SKILL/scripts/platform-book" ready
"$BOOK_SKILL/scripts/platform-book" figures "$NOTE"
"$BOOK_SKILL/scripts/platform-book" build "$NOTE" "$NOTE/signing-auth.ru.pdf"
"$BOOK_SKILL/scripts/platform-book" check-pdf "$NOTE/signing-auth.ru.pdf" \
  --expected-pages 14 --fonts "PT Serif" "PT Sans" "PT Mono"
sh scripts/check.sh
python3 scripts/check-self-test.py
```

Для записки принят предел **8–14 страниц**, включая обложку и оглавление.
Текущая сборка — **14 страниц**. Состояния архитектуры и открытых контрактов
перенесены в `book/ru/29-gde-my.md`; редакторское правило и три пары примеров —
в `editorial/notes/target-state-voice-pilot.ru.md`.
Он проверяется отдельно по результату `check-pdf`. Число страниц и встраивание
шрифтов не заменяют визуального ревью рисунков, таблиц, кода и переносов.

## Инструменты и артефакты

| Инструмент | Назначение и команда | Результат |
| --- | --- | --- |
| platform-book на закреплённой ревизии | `ready`, `figures`, `build`, `check-pdf` выше; Pandoc + Python WeasyPrint 70.0, pypdf 5.9.0, встроенные PT-шрифты | PDF рядом с исходниками; JSON вердикта в stdout |
| PlantUML 1.2026.6 и Graphviz | `plantuml -tsvg -nometadata -o ../diagrams editorial/notes/signing-auth/src/*.puml` | самодостаточные SVG в `diagrams/` |
| Python 3.12.15, `hashlib` | `hashlib.sha256(path.read_bytes()).hexdigest()` для каждой пары | `src/figures.json`: исходник, SVG и оба хэша; обновить после ревью рисунка |
| Poppler: `pdfinfo`, `pdffonts`, `pdftotext` | независимо проверить страницы, шрифты и извлечение текста | stdout или временные файлы в `.temp/` |
| Poppler: `pdftoppm` | `pdftoppm -scale-to 1400 -png editorial/notes/signing-auth/signing-auth.ru.pdf .temp/signing-auth-page` | временные страницы для визуального ревью в `.temp/` |
| `sh scripts/check.sh` | гигиена основной книги и пейпера; `editorial/` скрипт не охватывает | stdout; записка требует отдельной проверки текста |

В `src/` лежат редактируемые PlantUML-исходники. SVG в `diagrams/` — их
рендеры, объявленные в `src/figures.json`. Хэши обнаруживают дрейф, но не
доказывают семантическую верность рисунка: её проверяют вместе с текстом.
Ни новых продуктовых проверок, ни изменения исполняемого поведения записка
не вводит; описанные отказы — требования к будущим контрактам, а не результаты
криптографического интеграционного теста.
