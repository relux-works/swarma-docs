# Язык ядра Swarm Signer: Go, Rust или Swift

24 октября 2026 года. Исследовательская рекомендация; выбор реализации ещё не утверждён.

## 1. Рекомендация и границы задачи

Для полного набора требований рекомендуется **небольшое Rust-ядро с UniFFI, Swift-приложение и Matrix Rust SDK для носителя**. Главный аргумент — готовый путь через Matrix E2EE, cross-signing и мобильные bindings, используемый Element X. Это инженерный вывод из доступных реализаций, а не доказательство превосходства Rust на любой задаче. Go через gomobile остаётся сильной альтернативой, если главным станет буквальное переиспользование правил CLI, а Matrix E2EE будет отдельным компонентом. Swift разумен для продукта только на Apple, но отдельный Kotlin позже увеличивает число реализаций правил. [Matrix SDK][matrix-sdk], [Element X][element-x].

Swarm Signer должен собирать и проверять `swarm-envelope/2`, проверять цепочки доверия и гранты, получать реестр владельца из git и работать внутри приложений macOS/iOS. На границе подписи приложение предоставляет key provider: ядро передаёт точные подписываемые байты и получает подпись, без закрытого ключа. Совместимость с Go CLI требуется по общим векторам. Это условия сравнения, а не сообщение о готовой реализации.

Есть два ограничения, которые выбор языка не устраняет:

- Документированный Apple API Secure Enclave для рассматриваемой подписи использует **P-256**, тогда как условие для конвертов — **Ed25519**. Обещать аппаратную Ed25519-подпись через этот API нельзя. Обёртка key provider алгоритм не меняет. [Apple Secure Enclave][apple-se], [CryptoKit P-256][apple-p256].
- Запрет видеть закрытый ключ нужно адресовать конкретным ключам. Matrix E2EE использует собственные секреты устройства и ratchet-состояние. `OlmMachine` создаёт и хранит криптографическое состояние, предоставляет импорт/экспорт cross-signing secrets. Стандартный SDK нельзя объявить целиком лишённым секретов только потому, что подпись конверта вынесена в Swift. [OlmMachine][olm-machine].

Предлагаемая граница: ядро правил не владеет закрытыми ключами оператора; аппаратная подпись находится в платформенном адаптере; носитель владеет явно выделенным E2EE-хранилищем. Если требование означает отсутствие **любых** секретов во всём процессе общего ядра, эту границу надо изменить до реализации. Готовность SDK работать в таком режиме не проверена.

Уровень A1 означает проверенную цепочку E2EE-устройства к закреплённому master key; он не заменяет проверку гранта или подтверждение точного действия. Выбор SDK не изменяет действующий переходный режим доверия к человеческому входу и не вводит новый формат аттестации. Основание — раздел «Доверие к человеческому входу» в [редакционных решениях](../decisions.ru.md) и глава [«Путь сообщения и мост»](../../book/ru/07-soobscheniya-i-most.md).

## 2. Зрелость инструментария и сводное сравнение

Go Mobile поддерживает вызов Go из Objective-C/Java; Swift обращается к Objective-C API. Это существующий инструмент Go, но не интерфейс, автоматически повторяющий возможности современного Swift. В документации Wiki ещё встречается описание симулятора времён Go 1.5: её достаточно для общей схемы, но не для выбора сегодняшних архитектур и параметров сборки. Проверять нужно исходники команды и конкретную сборку. [Go Mobile][go-mobile], [gomobile bind][go-bind-command].

UniFFI поддерживается Mozilla, генерирует Swift/Kotlin bindings из описанных Rust-интерфейсов. Его руководство прямо отделяет генерацию bindings от доставки библиотеки на платформу: сборка target slices и упаковка остаются частью проекта. В опубликованном changelog есть исправления Swift async, утечек и concurrency, а также выпуск 0.32.1 от сентября 2026 года. Это свидетельство сопровождения, одновременно причина закреплять генератор вместе с runtime scaffolding. [UniFFI][uniffi], [changelog][uniffi-changelog].

| Критерий | Go + gomobile | Rust + UniFFI | Swift; Kotlin отдельно |
| --- | --- | --- | --- |
| Сохранение Go-правил CLI | Максимальное при настоящем извлечении пакета, без fork | Вторая реализация правил | Вторая, затем третья реализация |
| Мобильная граница | Objective-C-протоколы, ограниченные типы | Swift/Kotlin records, enums, objects, foreign traits | Внутри Apple границы FFI нет |
| Async key provider | Собственный адаптер поверх callback-интерфейса | Документированный async/await и foreign traits | Нативные protocols/actors/async |
| Matrix E2EE | mautrix-go; отдельно выбрать backend | matrix-sdk-crypto поверх vodozemac | Готовый Rust SDK из Swift либо отдельная квалификация иной библиотеки |
| Память | Go runtime и GC сверх состояния приложения | Нет Go GC; память SDK, executor и stores остаётся | Нет дополнительного Go/Rust runtime у чистого варианта; гибрид с Matrix Rust SDK его код сохраняет |
| Несколько библиотек | Независимые Go frameworks в одном процессе — интеграционный риск | Композиция компонентов возможна; зависимости и символы требуют контроля | Обычная композиция Swift packages; C/Rust-зависимости учитываются отдельно |
| Основная цена | Мобильная обёртка, lifecycle, E2EE assurance | Портирование правил, Rust/FFI toolchain | Повторение правил и проверок на каждой платформе |

Строки о стоимости — оценка архитектуры, не измерение трудоёмкости. Основания для типов и async: [gobind][go-bind], [UniFFI types][uniffi-types], [foreign traits][uniffi-traits], [async][uniffi-async]. Основания для Matrix и интеграции разобраны ниже. Численной оценки скорости разработки нет: не проверены ни объём извлекаемого Go-кода, ни опыт сопровождения Rust командой.

Для воспроизводимости просмотрены публичные исходники на ревизиях: Go Mobile `19777044486779222400e9ca16c4306f9c6dbfa9`, UniFFI `c31f4bc025c7a31eae56b49107f50e6d38e76bc7`, Matrix Rust SDK `8de215a0aa0026afa5754ae5f05a6d168d1a1d60`, mautrix-go `3a801b42501609da5c411a0a152a09997dc45fd2`. Это точки изучения, **не испытанная совместимая комбинация зависимостей**. Ни один из этих SDK здесь не собран для выпуска приложения.

## 3. Типы, async и обратный вызов в Swift

### Go

`gobind` разрешает подмножество типов: signed integers, floats, bool, string, byte slices, подходящие structs и interfaces. Возврат — без результата, один результат либо результат плюс `error`. Каналы, произвольные maps и generic API нельзя просто экспортировать как публичную модель Signer. Panic или исключение, пересёкшие границу, по документации завершают программу. Поэтому нужна маленькая фасадная библиотека с байтами и явными результатами. [gobind][go-bind].

Key provider технически реализуем: Go interface становится Objective-C protocol, который реализует Swift-объект. Но это ещё не Swift `async throws`: ожидание Face ID или внешнего устройства требует отдельного протокола завершения, отмены и владения запросом. Предложение — не удерживать блокировку ядра во время UI, не блокировать main actor ожиданием ответа из Go и не рассчитывать на то, что отмена Swift Task сама отменит goroutine.

Особенно опасен цикл владения: Go держит proxy Swift provider, а provider удерживает Go engine. Документация предупреждает, что такие циклы могут остаться живыми. Нужны явное закрытие engine, снятие callbacks и тесты отмены. Переиспользование пакета CLI не переносит автоматически корректный lifecycle в приложение. [gobind: reference cycles][go-bind].

### Rust

UniFFI передаёт поддерживаемые значения через собственную модель, а не произвольный Rust ABI. Поддерживаются целые обоих знаков, строки и byte buffers; для предметной модели доступны records и enums. Обобщённые Rust-типы и заимствования нельзя считать свободно экспортируемыми; интерфейс надо проектировать отдельно. Для timestamp/duration документация отмечает возможную потерю точности в Swift: для значимых байтов протокола следует сохранить исходное представление и нормативные правила преобразования. [Built-in types][uniffi-types].

Для provider предпочтителен foreign trait, реализованный в Swift. Старый отдельный `callback interface` в текущем руководстве мягко устарел. UniFFI документирует преобразование Rust futures в Swift async и Kotlin suspend, в том числе async-вызовы в иностранную реализацию. Это сокращает собственный glue-код относительно gomobile, но не освобождает Swift-объект от thread-safety. [Foreign traits][uniffi-traits], [callback interfaces][uniffi-callbacks], [async][uniffi-async].

Swift 6 support в руководстве назван частичным; там же отмечены rough edges вокруг `Sendable`, особенно async. Changelog содержит более свежие исправления. Следовательно, нельзя обещать полную совместимость по одной странице `latest`: нужны закреплённая версия, strict concurrency и сборка именно нашего provider. Для Matrix SDK следует прежде всего брать совместимую с ним версию UniFFI, а не самостоятельно обновлять генератор до максимальной. [Swift bindings][uniffi-swift], [changelog][uniffi-changelog].

### Swift

В чистом Swift правила, key provider и UI можно разделить protocols и actors без FFI. Это уменьшает число преобразований и позволяет явно провести UI-вызов через main actor. Такой выигрыш относится к своему коду: при подключении Matrix Rust SDK граница FFI остаётся в носителе. Отдельный Kotlin provider позже потребует самостоятельной проверки отмены, lifetime и ошибок. Знание Swift не служит доказательством корректности этого второго пути.

Для любого языка предлагается одинаковая проверка: успешно завершённая подпись возвращается ровно своему ожидающему вызову; отказ пользователя, отмена, отключение устройства и закрытие engine не дают отправить конверт. Рядом должен пройти обычный успешный вызов. Контрольный mutant — убрать проверку принадлежности ответа текущему запросу и показать, что тест ловит подстановку позднего ответа. Это план проверки будущего интерфейса, без назначения новых wire-полей или кодов отказа.

## 4. Криптография и аппаратные ключи

Для Ed25519 есть поддерживаемые примитивы во всех трёх вариантах: стандартный Go `crypto/ed25519`, Rust `ed25519-dalek`, Apple CryptoKit `Curve25519.Signing`. В последнем случае имя API не следует путать с X25519 key agreement. Swift Crypto предоставляет значительную часть API CryptoKit и на других поддерживаемых Swift-платформах. Выбор языка сам по себе не требует писать Ed25519 заново. [Go Ed25519][go-ed25519], [dalek][dalek], [CryptoKit Signing][apple-ed25519], [Swift Crypto][swift-crypto].

Наличие библиотеки не означает равенства всех verdicts на патологических входах. У dalek есть отдельный `verify_strict`; его документация объясняет различия проверок. Нельзя механически заменить Go verifier на «самый строгий» Rust и объявить полную совместимость: сначала спецификация допустимых подписей, затем векторы граничных случаев. Это касается и обратного направления: совпадение на валидных подписях ничего не говорит об ошибочном принятии некорректных. [VerifyingKey][dalek-verify].

Для конвертов предлагается проверять исходные байты, длины, неверные подписи и несовпадение ключа; конкретный набор допустимых кодировок должен прийти из нормативного пакета. Для CCJ-1 нельзя подставить обычную JSON-сериализацию с отсортированными ключами и считать её доказанным эквивалентом. Полный нормативный пакет `swarm-envelope/2` и его executable vectors здесь не квалифицированы; точные правила canonicalization и отказов не воспроизводятся и не изобретаются.

Secure Enclave P-256 и Ed25519 — разные алгоритмы подписи. Apple документирует создание неэкспортируемого P-256 ключа внутри Enclave; импорт произвольного существующего ключа в него не предусмотрен. Наличие software Ed25519 в CryptoKit не превращает её в Enclave-backed Ed25519. [Protecting keys][apple-se].

Есть несколько чистых направлений решения: аппаратный ключ с подходящим поддерживаемым алгоритмом; утверждённое протоколом использование аппаратной P-256 подписи; либо отдельно описанная защита программного Ed25519 ключа. Последнее **не равно** требованию «закрытый ключ никогда не покидает аппаратный модуль». Здесь ни одно направление не утверждается; выбор алгоритма и формата аттестации остаётся открытым. Смена языка не повод менять конверт или корень доверия.

«FIDO key» тоже недостаточно точно. WebAuthn assertion подписывает определённую протоколом структуру, связанную с authenticator data и client data, а не произвольные байты конверта как обычный Ed25519 signer. Способ использования конкретного устройства, его алгоритм и проверка user presence требуют отдельного адаптера и квалификации. Поддержка нужного режима выбранным физическим ключом **не проверена**. [WebAuthn signature][webauthn].

В предлагаемой модели provider получает полное точное действие, а не только непрозрачный дайджест для слепой подписи. UI показывает человеку смысл из тех же проверенных данных; ядро после возврата проверяет подпись ожидаемым публичным ключом. Это продолжает принятое правило о запрете слепой подписи из [редакционных решений](../decisions.ru.md), но не обещает защиты от компрометации всего приложения.

## 5. Matrix: библиотека, аудит и федерация

### Что действительно даёт Rust

`vodozemac` реализует Olm/Megolm и связанные криптографические операции. **Cross-signing и жизненный цикл устройств — уровень SDK, а не только ratchet-библиотеки.** Matrix Rust SDK отдельно предоставляет `matrix-sdk-crypto`, state machine без network I/O; полный SDK добавляет сеть, sync и stores. Подключить лишь vodozemac означает самостоятельно построить существенную часть клиентской логики. [vodozemac][vodozemac], [структура SDK][matrix-sdk].

Независимый отчёт Least Authority датирован 30 марта 2022 года. Начальная ревизия vodozemac — `7c11a501bc316a0bf92a5fe06fee8582aad24897`, проверка исправлений — `57d8d87a747653d6d7b7a53acb9a8d8f8de48285`. Отчёт описывает находки, включая работу с секретами и входными данными; это не утверждение «ошибок не было». Зависимости и не включённые отдельно bindings исключены из области аудита. Переносить этот аудит на текущую сборку Signer, весь Matrix SDK, UniFFI или федерацию нельзя. [Отчёт, область и результаты][vodo-audit].

Актуальность SDK проверяется отдельно от исторического аудита. Например, advisory SDK описывает пропущенную привязку user ID в зашифрованном to-device событии и возможность подмены при участии homeserver. Changelog содержит исправления sender binding и отдельного panic в стратегии выдачи ключей. Это особенно существенно для Signer: успешная расшифровка ещё не удостоверяет нужного субъекта команды. Перед выпуском нужны закреплённые зависимости с применимыми исправлениями; полный независимый аудит современной комбинации здесь **не подтверждён**. [Advisory][matrix-advisory], [crypto changelog][matrix-changelog].

### Что действительно даёт Go

mautrix-go заявляет E2EE, backup, cross-signing и interactive verification; его используют bridges и gomuks. Поэтому утверждение «в Go нет cross-signing» неверно. `goolm` — чистая Go-реализация Olm, отдельная от самого клиента. Публичный независимый аудит именно выбранной версии goolm в проверенных материалах **не найден**; отсутствие найденного отчёта не доказывает отсутствие аудита вообще. Вопрос об аудите есть в upstream issue, но сам вопрос не служит подтверждением. [mautrix-go][mautrix], [goolm README][goolm], [обсуждение аудита][goolm-audit].

В pinned исходнике `FetchKeys` формирует запрос по полным user IDs, обрабатывает device keys, сохраняет master/self-signing keys. Однако `resp.Failures` по серверам логируется, а после обработки функция возвращает `data, nil`. Вывод ограничен этой функцией: отсутствие общего `error` не доказывает свежесть ключей каждого удалённого участника. Над ней нужен контроль полноты результата и допустимого доверенного состояния; это не доказанная уязвимость всего SDK. [Pinned devicelist.go][mautrix-devices].

### Swift и доказательства федерации

SwiftUI-клиент Element X использует Matrix Rust SDK через FFI Swift package; это подтверждённый готовый путь для Swift-приложения. Старый `matrix-ios-sdk` сам описывает обёртку над Rust `OlmMachine`. Поэтому «взять iOS SDK» не всегда означает отдельное чисто Swift E2EE-ядро. Сопоставимый по области современный независимый аудит полностью Swift-реализации E2EE и cross-signing здесь **не подтверждён**. [Element X][element-x], [iOS SDK architecture][matrix-ios].

Федерация Matrix проходит между homeservers. Клиент спрашивает свой сервер о ключах полного удалённого user ID. Client-Server API определяет `master_keys`, `self_signing_keys`, сведения об устройствах и `failures` недоступных серверов; отсутствие user/device при достижимом сервере — другой случай. Изменения cross-signing приходят через device-list notifications и требуют обновления query. Получение чужого master key не доказывает его привязку к корню владельца. [Matrix Client-Server API v1.15][matrix-cs].

Серверная спецификация описывает распространение device-list updates, последовательности обновлений и восстановление списка при разрывах. Реализация Server-Server API в клиенте Signer для этого не нужна: сеть SDK и собственный homeserver должны совместно доставить данные. Клиент обязан проверить криптографические связи и применить собственную политику доверия. Наличие «federation module» в Go-библиотеке не даёт дополнительного разрешения удалённому отправителю. [Matrix Server-Server API v1.15][matrix-ss].

У Rust `OlmMachine` есть запросы ключей пользователей, получение identity/devices и обработка ответов исходящих запросов. При встраивании только crypto state machine приложение обязано само обслуживать network requests и sync; пропущенный цикл обработки оставит состояния неполными. Высокоуровневый SDK уменьшает этот glue-код. [OlmMachine][olm-machine].

| --- | --- | --- |
| Go / mautrix-go | Запрос чужих устройств и cross-signing keys через клиентский API; обработка результатов и ошибок удалённых серверов | Наша политика на частичном ответе, ротации master key и устаревшем кэше |
| Rust / Matrix SDK | Общая state machine для ключей/identity, sync в полном SDK; использование в мобильных клиентах | Наша привязка owner root, повторный допуск после ротации и отказ при неполных данных |
| Swift / Rust SDK | Тот же SDK через мобильный binding | Те же проверки плюс корректность отображения verdict в Swift |
| Чистый Swift / другая библиотека | Подходящая библиотека полностью не квалифицирована | Весь требуемый путь cross-signing и обновлений удалённых устройств |

Предлагается общий приёмочный сценарий на двух независимых homeservers: удалённое устройство с цепочкой к закреплённому master key допускается по соответствующей политике; новое неподписанное устройство и подмена master key не наследуют доверие. Дополнительно: удаление устройства, потеря части key-query response, reconnect после пропущенного sync и ротация после офлайн-периода. После каждого отказа — отсутствие разрешённого действия; рядом — успешное восстановление доверия законным способом. Сужающий mutant отключает проверку закрепления master key: подмена обязана стать видимой тесту. **Такой стенд здесь не запускался**, и end-to-end федерация Signer не объявляется проверенной.

## 6. XMPP и OMEMO позже

Rust Matrix stack не предоставляет готовую реализацию OMEMO только потому, что тоже использует ratchets. XEP-0384 отдельно задаёт discovery устройств, публикацию списков и bundles, установку сессий, доставку и проверки. Просмотренная версия — 0.9.1 от 6 апреля 2026 года, статус Experimental. Совместимость конкретной библиотеки с этой редакцией, а не только с названием «OMEMO», надо проверять явно. [XEP-0384][omemo].

| Язык | Обоснованный исходный кандидат | Что остаётся установить |
| --- | --- | --- |
| Go | `xmpp-go`: upstream описывает OMEMO v2, PEP device lists и bundles | Заявленная поддержка не подтверждает аудит и обработку отказов федерации; для Signer не квалифицирована |
| Rust | Отдельный XMPP/OMEMO адаптер рядом с Matrix | Нельзя переносить аудит vodozemac или Matrix SDK на OMEMO; библиотека ещё не квалифицирована |
| Swift | Martin с дополнительной MartinOMEMO | README подтверждает наличие XEP-0384 поддержки, но не полную квалификацию нужной редакции, аудита и федерационных отказов |

[Martin][martin] с [MartinOMEMO][martin-omemo] даёт конкретный Swift-кандидат, а не причину переписывать ядро. [Go OMEMO guide][xmpp-go] описывает получение списков и bundles, но не является испытанием двух серверов. [xmpp-rs][xmpp-rs] — кандидат для Rust XMPP-слоя; просмотренная страница подтверждает существование библиотеки, но не требуемую OMEMO state machine, аудит или федерационную квалификацию. Во всех вариантах Signer должен адресовать удалённый аккаунт целиком, получать его device list и bundles по предусмотренному XMPP-пути и отдельно проверять доверие. Работа на одном сервере не заменяет проверки доставки через server-to-server federation.

Предлагаемый минимум — два XMPP-домена: подписанное/доверенное устройство работает; добавленное неизвестное устройство, замена списка, недоступный remote PEP и запоздалое уведомление не дают повысить доверие. После восстановления связи легитимное изменение проходит явный путь проверки. Векторы конвертов проверяют правила Signer; они не покрывают автоматически XMPP discovery и состояние OMEMO-сессий. Исполнение этой проверки отложено до выбора адаптера; положительного заключения о федерации OMEMO ни для одного варианта сейчас нет.

## 7. Frameworks, память и реальные приложения

Ограничение Go следует формулировать как риск **нескольких независимо собранных Go runtime в одном процессе**, а не «в iOS можно только один framework». IPtProxy объединяет Go-компоненты в одну библиотеку именно из-за конфликтов символов нескольких gomobile frameworks. В Go upstream есть воспроизведение panic с несколькими c-shared libraries. Конкретный вид линковки отличается, поэтому это предупреждение, а не универсальный эксперимент над всеми xcframework. [IPtProxy][iptproxy], [Go runtime issue][go-multiple].

Практический план для Go — одна общая сборка всех Go-пакетов для данного executable. Она может соседствовать со Swift/C/Rust frameworks. Если приложение уже использует другой независимо поставляемый Go SDK, возможность его объединения становится критерием выбора. Параметр Objective-C prefix не следует принимать за решение конфликта runtime-символов. App и extension надо рассматривать как отдельные executable и отдельно проверять их зависимости.

У UniFFI документирована композиция нескольких компонентов в одну библиотеку через scaffolding re-export. Общего запрета на второй framework, аналогичного gomobile-сценарию, не установлено. Это не обещание отсутствия коллизий: два экземпляра одной native-зависимости или несовместимые generated bindings всё ещё требуют проверки. Для Signer предлагается общий Cargo graph с Matrix SDK и одна согласованная цепочка генерации. [UniFFI component composition][uniffi-composition].

Go добавляет runtime, GC и состояния goroutines. Rust не добавляет Go runtime, но полный Matrix SDK включает существенно больше простого verifier: сеть, async executor, базы и crypto store. Swift использует собственные runtime/ARC; подключённый Rust SDK остаётся в бинарном составе. Из этого **не следует численный рейтинг** по размеру, RSS или батарее. Размер архива xcframework с несколькими slices нельзя сравнивать с размером конечного stripped executable.

Apple предупреждает о меньших лимитах памяти extensions относительно foreground app; конкретные ограничения различаются. Tailscale в публикации 2021 года описывал работу Go в iOS Network Extension с бюджетом 15 MB и оптимизацию linker/runtime footprint. Это исторический бюджет конкретного продукта и extension point, а не текущий универсальный предел всех iOS extensions и не замер Signer. [Apple extensions][apple-extensions], [Tailscale linker][tailscale].

До выбора языка предлагается измерить release-варианты с одинаковой функцией: пустое приложение; verifier без сети; verifier плюс Matrix SDK; нужный extension. Для каждого — прирост конечного executable, cold start, peak physical footprint при sync, при массовом key query и после отмены provider. Ещё нужны реальный iPhone, выбранный тип extension и пределы времени его работы. Таких замеров здесь **нет**; небольшой compiler probe ниже их не заменяет.

Производственные свидетельства различаются по тому, что доказывают:

- **Element X iOS/Android:** общий Matrix Rust SDK, SwiftUI на iOS, FFI Swift package. Это прямое свидетельство нужного класса интеграции, но не проверки нашего протокола. [Element X][element-x].
- **WireGuard Apple:** Swift package связывает `WireGuardKit` с отдельно собираемой Go bridge library для iOS/macOS. Это свидетельство доставки Go в Apple-приложении; README описывает собственную build integration, поэтому нельзя приписывать ему доказательство удобства именно gomobile. [WireGuardKit][wireguard].
- **Tailscale:** свидетельство эксплуатации Go в ресурсоограниченном iOS-процессе вместе с реальной ценой оптимизации. Это не основание переносить их измерения на другую нагрузку. [Tailscale][tailscale].

## 8. Совместимость с CLI, git и опыт команды

Цена Rust-варианта — второй исполнитель правил рядом с Go CLI. Нужно перенести canonicalization, проверку конверта, цепочек и грантов, состояние отзыва и чтение доверенного снимка реестра. При Swift/Kotlin число исполнителей правил становится ещё больше. При Go общий исходный пакет уменьшает этот риск, **только если** мобильное приложение действительно использует его без отдельной логики и окружение CLI не проникло в библиотеку.

Предлагается сначала выделить переносимое ядро правил и отдельно транспорт, clock/storage, git-sync и provider. Нельзя включить CLI целиком и считать доступ к диску, процессам и Git такой же средой, как на desktop. Ни переносимость сегодняшнего a2a-пакета на iOS, ни точный объём его извлечения здесь не проверены. Это сохраняет преимущество Go как гипотезу, не превращая его в оценку «почти бесплатно».

Для git-реестра язык не решает, какую голову доверять. Fetch приносит объекты; проверка подписи commit не определяет сама по себе допустимость отката или состояние отзыва. Предлагается давать ядру проверяемый неизменяемый снимок и отдельно контролировать его происхождение, принятую ревизию и атомарное обновление. Прерванная синхронизация не должна оставлять частично доверенный реестр. Конкретные git libraries, подписи и iOS background sync ещё не квалифицированы ни для одного языка; форматы снимка и anti-rollback здесь не назначаются.

Общие vectors должны иметь нормативное ожидаемое поведение, а не только сравнение Rust со «всегда верным Go». Пакет стоит версионировать вместе со спецификацией; обновление CLI и приложения должно явно указывать поддерживаемую версию. Предлагаемые группы после сверки с нормативным форматом:

| Область | Положительный контроль | Запрещённое поведение |
| --- | --- | --- |
| Canonicalization | Разрешённое представление даёт ожидаемые точные байты | Неподдерживаемый ввод молча меняется в другое подписываемое сообщение |
| Подпись | Известный ключ принимает ожидаемую подпись | Иной ключ или изменение подписанных байтов сохраняет допуск |
| Цепочка и грант | Делегирование внутри полномочий родителя | Расширение области или срока дочерним грантом |
| Реестр | Допустимое атомарное обновление | Отзыв или неподтверждённый снимок игнорируется |
| Provider | Успешное подтверждение точного действия | Отмена и поздний ответ создают отправку |

Названия — группы проверок, не новые поля конверта. Для каждого нового допускающего правила нужен bounded mutant, удаляющий именно эту проверку, рядом с обычным успешным сценарием. Статические vectors ограничивают расхождение реализаций, но не доказывают корректность UI, устройства, базы после crash и сети при федерации. Эти пути требуют собственных integration tests.

Известно, что приложения написаны на Swift, CLI на Go; у оператора нет опыта gomobile. Это условия задачи. Уровень практического Rust/UniFFI и Kotlin-сопровождения **не установлен**; выводить его из наличия этих языков в экосистеме нельзя. Нужен владелец поддерживаемого мобильного toolchain, обновлений SDK и разбора incident. Оценки в человеко-днях без этого и без извлечения Go-пакета не подтверждены.

Если Android остаётся неопределённым далёким направлением, полезный промежуточный вариант — Swift-правила и готовый Matrix Rust SDK, без самостоятельной E2EE. Он уменьшает собственный FFI для правил, но сохраняет второй verifier относительно Go и будущий перенос на Kotlin. Если общий мобильный core требуется уже сейчас, Rust лучше соответствует этой цели.

## 9. Дешёвая проверка и условия пересмотра

Проверка выполнена 24 октября 2026 года без генерации ключей, обращения к Keychain, запуска приложения или симулятора. Использованы Apple Swift **6.4** (`swiftlang-6.4.0.34.1`, clang `2100.3.34.1`), swift-driver `1.168.6`, Xcode **27.0 / 27A266a**, iOS Simulator SDK **27.0**, target `arm64-apple-ios18.0-simulator`. Python **3.15.0** измерял wall time через monotonic `perf_counter`. Доступный Go — **go1.25.5 darwin/arm64**; gomobile/gobind и Rust toolchain не найдены в PATH. Они не устанавливались.

Положительный probe содержит только проверку типов существующих API:

```swift
import CryptoKit
import Foundation
func verify(_ key: Curve25519.Signing.PublicKey,
            _ signature: Data, _ bytes: Data) -> Bool {
    key.isValidSignature(signature, for: bytes)
}
func sign(_ key: SecureEnclave.P256.Signing.PrivateKey,
          _ bytes: Data) throws -> Data {
    try key.signature(for: bytes).rawRepresentation
}
```

Негативный control заменяет доступный Enclave-тип предполагаемым Ed25519-типом:

```swift
import CryptoKit
func unavailable(_ key: SecureEnclave.Curve25519.Signing.PrivateKey) {}
```

В отдельном временном каталоге команды воспроизводятся так; локальные переменные задают только пути созданных файлов и compiler cache:

```sh
sdk=$(xcrun --sdk iphonesimulator --show-sdk-path)
xcrun --sdk iphonesimulator swiftc -typecheck \
  -target arm64-apple-ios18.0-simulator -sdk "$sdk" \
  -module-cache-path ./module-cache positive.swift
xcrun --sdk iphonesimulator swiftc -typecheck \
  -target arm64-apple-ios18.0-simulator -sdk "$sdk" \
  -module-cache-path ./module-cache negative.swift
```

| Проверка | Exit | Wall time | Что установлено |
| --- | ---: | ---: | --- |
| Positive | 0 | 3.329 s | Оба использованных API доступны для type-check этого simulator target |
| Negative | 1 | 0.161 s | Отказ именно из-за отсутствующего `Curve25519` в `CryptoKit.SecureEnclave` |

Это один проход, не performance comparison: второй вызов использовал прогретый cache. Проверен текст ожидаемой compiler diagnostic, а не просто любой ненулевой exit. Probe не доказывает аппаратную подпись, криптографическую корректность или работоспособность FFI. Gomobile xcframework не собиралась: callback уже описан upstream, а без установленного инструмента это потребовало бы отдельной установки и pinning. Вместо такого испытания дешёво проверено ограничение, общее для всех вариантов. Сборка Rust/UniFFI, размеры и runtime federation остались непроверенными.

Рекомендация пересматривается при следующих наблюдениях:

1. **В пользу Go:** извлечённый пакет проходит нормативные vectors на iOS, provider корректно отменяется, единая Go-сборка совместима с зависимостями приложения; память укладывается в согласованный бюджет, а требуемый уровень assurance E2EE подтверждён. Тогда экономия на единой реализации правил может перевесить преимущества Rust.
2. **В пользу Swift:** продукт ограничен Apple, Android не входит в подтверждённый план, а команда уверенно сопровождает Swift-правила с Rust SDK только для носителя. Тогда свой второй FFI для небольшого ядра может оказаться лишним.
3. **Против предлагаемого Rust:** необходимый Swift 6/provider path не работает на закреплённой комбинации без обходов; подходящий SDK не укладывается в бюджет нужного extension; нет ответственного за Rust-сопровождение. Это проверяемые условия, а не заранее установленные факты.
4. **До любого выпуска:** согласована аппаратная схема ключей и значение требования «ядро не видит ключ»; доступны нормативный формат и shared vectors; пройдены тесты двух homeservers, отказов provider и атомарного обновления реестра.

Следующий разумный эксперимент — закреплённая минимальная Rust/UniFFI библиотека с verifier и async Swift provider, использующая ту же версию bindings, что выбранный Matrix SDK. Сначала — simulator build и cancel/late-callback controls; затем — отдельный санкционированный опыт на физическом устройстве с тестовыми ключами. Исследование рекомендует этот путь, но не выдаёт его за уже реализованный Signer.
